# Analysis pipeline

The Python in this folder turns the owner's public data releases into the aggregate files under `public/data/` that every page reads, and imports them. It never scrapes races and never connects to the live ingestion database: every input is an immutable, checksummed GitHub release. This file is the calculation, import and per-release contract: which release is read, what each module writes and what verifies it, and the conventions the independent verifiers follow. The standing rules are in [AGENTS.md](../AGENTS.md), the commands in the [operations runbook](../docs/OPERATIONS.md), and the files and how to open them in [ACCESS.md](ACCESS.md).

## The adopted release

`release.json` pins the main pipeline and `weather-release.json` the weather screen. Both hold only `repository` and `tag`, and they always name the same tag. Read it from the pin, never from a document:

```bash
python -c 'import json; print(json.load(open("analysis/release.json"))["tag"])'
```

On October 30, 2026 both pins name **`private-export-20261021-1050`** in `koolkam00/pace-notes`, adopted by PR #78 (merged as `39f3057` on October 22, 2026); its source, calculation and import evidence is in the [1050 refresh record](../docs/REFRESH_20261021_1050.md). A pin selects an input. It does not certify a calculation, an import or a deployment: what production serves is a separate fact, recorded in the handoff's [Current state](../docs/PROJECT_HANDOFF.md#current-state) (on October 30, 2026 at 23:30 UTC, production `/data/live.json` named the same tag). The half-marathon pages have their own pin, `half-release.json` ([below](#half-marathons-public-source-pages-show-aggregates)). Source files, calculations and output metadata keep metric units; miles and per-mile paces are website display conversions.

**Tag, bundle id and `--expected-export`.** Every pack records `input_export_id`, which `build_pacing.py` makes from the tag by changing `private-export-` to `private-` (an `htw-db-*` tag stays as it is). The importers' `--expected-export` must equal it, `private-20261021-1050` under 1050; any other value is refused (`import_packs.py`: "Artifact belongs to a different export."; `import_personalized.py` by an assertion). `calculation_provenance.py` then requires the exact reviewed builder hashes for the audited bundle ids `private-20260911-1107`, `private-20260912-0934`, `htw-db-2026-10-16-1652` and `private-20261021-1050`. Every identifier the releases use is in [data architecture](../docs/DATA_ARCHITECTURE.md#identifiers).

## Release archives and the downloader

`download_release.py --bundle CORE|FULL [--tag TAG] --output DIR` reads `--tag`, or the pin's tag when it is omitted, and accepts only `private-export-*` and `htw-db-*` tags. It decides the members an archive must hold from the asset's name first, then the tag (`expected_members`). The eight base members are `race_records.parquet`, `race_conditions.parquet`, `course_profiles.parquet`, `course_segments.parquet`, `sources.parquet`, `races_summary.json`, `MANIFEST.json` and `README.md`; FULL always adds `features.parquet`.

| Layout | CORE | FULL | Releases |
| --- | --- | --- | --- |
| `htw-private-export-*` assets | the 8 base members | 9 | 1107, 0934 |
| `htw-db-*` | 12: also `EDITIONS.json`, `CHANGE-REPORT.md`, `SHA256SUMS.txt`, `ID-CONTRACT.md` | 14: also `FEATURE-FIELD-NOTES.md` | 1652 |
| `pace-notes-*` | 16: also `EDITIONS.json`, `EDITION-CHECKSUMS.csv`, `CHANGE-REPORT.md`, `SHA256SUMS.txt`, `ID-CONTRACT.md`, `FEATURE-FIELD-NOTES.md`, `edition_meta.parquet`, `record_flags.parquet`; 17 with `MATCHING.md` from 1050 on | 17; 18 from 1050 on | 0829 (reviewed, not adopted), 1050 |

A release may split an archive into numbered parts (`….tar.gz.part-00`, `-01`, …; first in 1050's FULL). The downloader joins them in order, checks each part's size and GitHub digest, and requires the joined archive's SHA-256 to be listed in the release's `RELEASE-SHA256SUMS*.txt`: a split archive without that file is refused, and when a release publishes one, a single archive must be listed in it too. It rejects unsafe, duplicate and unexpected members, stops above 8 GiB extracted, writes every member straight into `--output` and records the tag, the archive and part digests, the release checksum file and the manifest digest in `provenance.json`. The asset list comes from `api.github.com` (a `GH_TOKEN` or `GITHUB_TOKEN`, if set, is sent only there, for the rate limit); the bytes come from `github.com` download URLs that carry no credentials.

`audit_release.py --input FULL --core CORE --previous PREV --output …/release-contract.json` checks the shared members between CORE and FULL, raw/feature alignment and timing units, and for `htw-db-*` and `pace-notes-*` releases every `SHA256SUMS.txt` line and the producer's per-edition counts. `--previous` takes the previously adopted release's input folder and reports the raw-record delta in total, by edition and by column: 1050 against 1652 added 412,943 records, deleted 794 (Amsterdam 2020) and changed none in place; 1652 against 0934 added 569,263, deleted 116,287 and changed 242,649. Record IDs are therefore not stable across releases ([AGENTS.md](../AGENTS.md) rule 10). The producer's contract texts are evidence, not proof (1652's `ID-CONTRACT.md` and `FEATURE-FIELD-NOTES.md` still named the 1107 freeze): identity is checked at run time ([below](#identity-and-chronology)).

## Running the pipeline

Run from the repository root with Python 3.12 (as in CI) and `analysis/requirements.txt` (DuckDB 1.4.4, NumPy 2.5.3 and pandas 3.0.5, which the half builders use). The importers and verifiers need Node on `PATH`; the half source recount opens SQLite with `node:sqlite`, which the Half marathon workflow runs on Node 22. The commands, with `TAG`, `IN`, `WORK` and `PREV` derived from the pin, are in [operations](../docs/OPERATIONS.md), in this order:

1. [Reproduce and audit the input](../docs/OPERATIONS.md#reproduce-and-audit-the-current-input): download CORE and FULL, inspect, audit against the previous release, run every Python test. A candidate release is audited with `export TAG=<new tag>` before any pin changes ([release intake](../docs/OPERATIONS.md#release-intake)).
2. [Calculate](../docs/OPERATIONS.md#calculate-all-owned-outputs): the 33 packs and the personalized engine, the findings, the weather screen, the supporting study and the runner lookup.
3. [Validate and import](../docs/OPERATIONS.md#validate-import-and-publish): both pack importers with `--expected-export`, the weather file, then the study and lookup importer, which also writes `public/data/live.json`.
4. [Runner context](../docs/OPERATIONS.md#runner-context-refresh), which binds the imported runner manifest; then [all-finisher context](../docs/OPERATIONS.md#all-finisher-context-refresh) and [fast start](../docs/OPERATIONS.md#fast-start-analysis-refresh).
5. [Stories, tool data and terrain splits](../docs/OPERATIONS.md#data-story-refresh), which bind the runner and runner-context manifests.
6. [Top 100 charts](../docs/OPERATIONS.md#top-100-charts-refresh), which bind the runner manifest and the weather evidence and read the stories' course geometry.
7. [Half](../docs/OPERATIONS.md#half-refresh), which binds the adopted release, the runner manifest, the weather evidence and two marathon files from steps 5 and 6.
8. `npm run verify:data` and `npm run build`.

Each step binds the outputs of the steps before it by hash, so a change to an earlier step means rebuilding every later step that binds it; relabelling a hash instead is never allowed. Build into a fresh folder, verify it there with the verifier's `--input`, and copy it into `public/data/` only after it passes.

## Independent verification conventions

A published number is trusted because a second program, written separately, gets the same number from the same public inputs. The general practices are in [AGENTS.md](../AGENTS.md#practices-that-have-paid-off); these are the conventions the verifiers in `scripts/` follow, with where each lives.

- **Recounts import no calculation code.** Each recount rebuilds its values from the checksum-verified published runner shards (the half source recount from the source files), with its own parser and cohort, and never imports a Python builder or trusts a builder's cohort (the first lines of `verify-insights`, `verify-charts`, `verify-all-finisher-context`, `verify-fast-start`, `verify-half` and `verify-half-source` say so). Where a verifier also renders the site's own code, as `verify-tools` does, the numbers it checks come from a model of its own (`scripts/lib/terrain-model.cjs` for the terrain shares). A family without a recount is never mistaken for a recounted one: `verify-insights` lists such families as `generic_only`, and `verify-charts` fails on a registered chart that has no recount.
- **Exact decimal cross-products at band edges.** A ratio is compared with a band edge by cross-multiplying the recorded decimal times, never by a binary division: `opening_band_for_times` in `build_fast_start.py` (Python `Decimal`), the opening bands of `build_fast_start_all.py` (decimal subtraction, then cross-multiplication) and BigInt rationals in `verify-fast-start.cjs` and `verify-fast-start-all.cjs`. For example, 2,850 s for 10 km against 12,658.5 s for 42.195 km is exactly 5% faster, where a binary division gives −5.000000000000004%.
- **Two fixed tolerances, the same in Python and Node.** The sustained-slowdown test is `pace / baseline − 1 + 1e-12 ≥ 0.25` (`RATIO_EPSILON` in `build_fast_start.py` and `build_public_explorer.py`, the same `1e-12` in `insights_data.py`, `insights_kick.py` and the verifiers), so an exact decimal boundary counts and a value 1e−9 below it does not. Section paces are held to 120–1,200 s/km (2–20 min/km) with a 1e-8 s/km tolerance (`PACE_BOUND_EPSILON` in `build_fast_start.py`, reused by `insights_data.py` and `half_marathon.py`; the same `1e-8` in the verifiers), and `PACE_EPSILON` (1e-8 s/km) snaps the all-finisher early-pace band edges at 270, 330 and 390 s/km. Source times are millisecond-resolution, so neither tolerance moves a real record across a boundary.
- **Python's rounding, reproduced in Node.** A Node recount of a value the Python builder rounded uses Python's rule, round half to even on the exact binary value: `pyRound` in `scripts/half/derive.cjs` (100.25 to one decimal is 100.2; `toFixed(1)` gives "100.3"). `toFixed` is right only where a check reproduces what a page itself prints with `toFixed`. Shared parity fixtures hold the two sides together: `scripts/half/fixtures/parity.json` (quantiles and published seconds; `test_half.py` and `verify-half` both read it) and [`course_terrain/fixtures/parity.json`](course_terrain/fixtures/parity.json) (the terrain model; `test_course_terrain.py` and `verify-tools`).
- **Every published group is counted against its floor.** The pacing, story, chart, fast-start, all-finisher and half builders publish a group only at 100 finishes or pairs (`MIN_CELL`), and the all-finisher and half builders a claim across editions only at 3 editions (`MIN_EDITIONS`); `import_packs.py` refuses a pack whose `n` is under 100. Open-ended tails and sex bins count like any other group: `check_published` in `half_common.py` fails an `under_lo` or `at_or_over_hi` tail under 100, and `verify-half` checks both tails of every histogram and sex bin. The check runs both ways where the recount can: `verify-insights`' projector check requires every published cell to match the recount and every recount group of 100 or more to be published. A tail under the floor narrows the published range; the floor is never lowered ([AGENTS.md](../AGENTS.md) rule 13).
- **Frozen lists, pinned inputs, loud failures.** Reviewed decisions are frozen as data and every input they rest on is pinned by SHA-256, so a changed input fails instead of drifting. `source_quality.py` applies a policy only to the exact tag it was reviewed for; the pacing workflow inspects an unreviewed tag and then fails. `build_half.py` recomputes every half screen and fails unless it equals the frozen list in the policy file, checks the corrected metadata's digest and the 72 withdrawn stamps against it, and fails on any count that differs from the reviewed one (`--accept-counts` only for a reviewed refresh, after reading every change). `verify-half-source` requires the frozen policy's rule text to equal its own constants. `build_course_terrain.py` refuses a new `course_profiles.parquet` hash until the correction registry is re-based on it. `calculation_provenance.py` refuses a pack whose builder hash is not the reviewed file.
- **Receipts for checks CI cannot repeat on every change.** The half source recount writes `docs/evidence/half/source-recount.json` (a date, the bound digests, the counts checked, no rows), and `verify-half` fails in CI while that receipt does not bind the current manifest and recount scripts. A skipped CI job is not a pass ([operations](../docs/OPERATIONS.md#ci-workflow-map)).

## Timing and source-quality contract

- Parse raw elapsed strings as H:MM:SS or M:SS; require all nine increasing checkpoints at 5, 10, 15, 20, 25, 30, 35, 40 and **42.195 km**, despite the `split_42_2km` field name. Do not interpolate missing splits or halfway times.
- Deduplicate equivalent records ignoring database IDs, ingestion timestamps and source URLs. Keep finishes from 90 minutes to 12 hours and every section from 2 to 20 min/km. These bounds can exclude real unusual performances.
- Apply [source_quality.py](source_quality.py) after timing checks. Its release-specific reviewed exclusions cover invalid grids (including grids that mix timing bases, mats that stopped recording partway through a field and a virtual edition), incomplete ingestion, unresolved HOLD editions and selected fields (top-finisher lists, and Boston 2013's finishers cut off when the race was stopped). Excluded editions do not supply current outcomes or earlier benchmarks. Do not exclude additional editions merely for being small.
- Reconcile `raw = duplicates_removed + missing_or_unparsed + non_increasing + outside_quality_bounds + source_quality_excluded + eligible`. `timing_eligible = source_quality_excluded + eligible`. The policy's edition counts and hashes travel with every output.
- **The adopted cohort (1050**, from `cohort` and `source_quality` in `public/data/runners/manifest.json`, the same in every pack): raw 5,327,504 in 298 editions and 34 cities; duplicates removed 0; missing or unparsed 882,266; non-increasing 25,098; outside the bounds 12,430; timing-eligible 4,407,710; source-excluded 298,961 in 41 editions (`RULES_1050`, policy SHA-256 `ba7749ee…2508`); **eligible 4,108,749 finishes in 215 editions from 27 cities**. Historical: 1652 had 4,027,044 timing-eligible, 155,277 excluded (30 editions) and 3,871,767 eligible (211 editions); 0934 had 3,595,426, 78,090 (11 editions) and 3,517,336. The full table is in [data architecture](../docs/DATA_ARCHITECTURE.md#measurement-and-eligibility).
- Missing age or recorded gender alone does not remove a valid finish from All. Exact-age/gender comparisons retain their own coverage rules. Feature `valid_splits` is a different population.
- Compare 0–20 with 20–40 km at equal distance; do not call these measured half-marathon splits. Runner-normalized median profiles need not integrate to zero even though each individual's normalized profile does.
- Chart cells generally require 100 finishes. Matched strata and edition comparisons have additional documented minima. These are reliability rules, not restrictions on access to full records. Finish counts are not unique-runner counts.

## Identity and chronology

Canonical record IDs are enabled only for the explicitly audited releases in `CANONICAL_ID_RELEASES` (`build_extended.py`): `private-export-20260911-1107`, `private-export-20260912-0934`, `htw-db-2026-10-16-1652` and `private-export-20261021-1050`. Each uses canonical raw `id` / feature `record_id` after runtime checks of unique matching sets and recorded labels, and the candidate join additionally matches finish and all nine section durations to milliseconds. `private-export-20261021-0829` was audited and not adopted (its FULL lacked the producer's cross-race identity; [review](../docs/REFRESH_20261021_0829.md)). Legacy September 7 reproduction retains one-to-one edition/name/full-timing matching because those numeric ID namespaces are incompatible. Never join by row order or apply the newer contract retroactively.

Cross-race IDs remain supplied candidates. Retain non-ambiguity, consistent recorded gender, inferred birth-year span at most two years and no duplicate edition. Recompute recent best from the two strictly earlier calendar years; exclude all current/same-year outcomes. Earlier-best improvements use all strictly earlier years, not a claimed lifetime PB. Supplied PB/ability/next-race fields never supply pre-race covariates.

Feature race dates remain null. Dated comparisons use complete, unique supplied edition-date coverage. Pair analyses require uniquely observed endpoint years; recorded return requires subsequent home-city edition coverage. Missing later records do not establish retirement. Course historical validity is unavailable except Warsaw's supplied start year (2019), so terrain is a supplied-route proxy, attached only inside a supplied validity interval.

## Packs, weather and the two importers

The pipeline calculates eight foundation and 25 extended packs (the research archive, all 33 named in `pack_registry.json`), plus the 12-path personalized engine supplying the [essential ten](../docs/TOP_TEN_ANALYSES.md). `build_pacing.py` writes the eight; `build_extended.py` writes the other 25 and then calls `build_personalized.generate` on the same prepared cohort/linkage tables. Do not run a partial extension import or replace the current 90–720-minute personalized result with an older 150–270-minute artifact. `write_findings.py` generates narrative results from aggregate tables and records its own script hash. Group running and congestion remain limited by missing physical-proximity/start-offset measurements.

The [weather screen](../docs/WEATHER_ANALYSES.md) evaluates humidity, four-hour warming and wind with a model and publication gate fixed across refreshes: all three candidates are rerun and retained in the audit, and current ready decisions determine routes. Do not force humidity to remain withheld or wind/warming to remain published. Review weather input identity, policy/script hashes, cohort reconciliation, all three decisions and edition values before copying its JSON to `public/data/weather/evidence.json`; weather is outside both import contracts and has its own verification.

The aggregate ZIP must contain `ext_pack_name/pack_meta.json`, `summary.json` and referenced `tables/*.csv`, with all 33 names in `pack_registry.json`. The personalized ZIP contains only `ext_personalized_guide/` and its JSON files. ZIP the contents of each output directory, not an extra parent folder. The 33-pack importer requires the complete registry and validates before replacing only its owned folders; the personalized importer validates every shard/CDF/cell and writes compact JSON with transport hashes. Artifact limits are 20 MB uncompressed for the 33-pack archive and 512 MB for personalized output; investigate unexpected growth rather than dropping required cells.

The site checks source/pin consistency, raw/timing/source-exclusion reconciliation, finite values, observed cohort counts, strict target boundaries, route readiness, source labels and unit conversions. ## Personalized engine

The engine retains 12 calculation paths: achieved-time pacing, earlier-benchmark opening, exact-threshold nearby finishes, age contrasts, terrain, opening/late pacing, checkpoints, course outcome spread, edition-weighted temperature, threshold context, paired returns and earlier-best gains. The primary ten are mapped in `lib/ten-analyses.ts`. The earlier guide's address, `/research/personalized`, redirects (308) to `/research` (`vercel.json`; checked on the live site October 30, 2026).

Targets are every whole minute from 90 through 720 with strict finish < target. Achieved-time bands use 43 fifteen-minute presets; exact thresholds do not interpolate. Exact ages are 18–24, then five-year bands through 85–89. Previous time selects a 15-minute band of recorded bests in the two earlier years. Broader cohorts are explicitly labeled; a course never silently falls back to another city.

Checkpoint cells use 20/30/35 km, two-minute elapsed bands with an exclusive upper endpoint, and optional recent-section trend; they do not use a prior-time filter. Their historical proportions are not validated individual probabilities. A separate forecast pack trains only before the latest three observed years and evaluates all models on the same later eligible cohort.

## Half marathons (public source, pages show aggregates)

The half pages read `public/data/half/`, built from the owner's public CC BY 4.0 half snapshot and its runner-links build (`half-dataset-20261029-1202`, doi:10.6084/m9.figshare.34858428.v1) with verified status from the corrected edition metadata of `half-dataset-20261029-2157`, all pinned by SHA-256 in `half-release.json` (schema 2). An edition is verified only when it is stamped in both the snapshot and the corrected metadata (the pin's `metadata_correction.applied`: "verified = stamped in both"). The pin keeps the first private releases' names (`half-snapshot-20261029-1133`, `runner-links-20261029-1156`) as `private_tag`, the identities the policy and counts are keyed by, and its `marathon_release` must equal the tag in `release.json`. The pages publish aggregates only: every shown group holds at least 100 finishes or pairs, and a claim across editions rests on at least 3 editions. The half work was merged to `main` by PR #85 (`a2c6e507`, October 30, 2026); its deployed state is in the handoff's [Current state](../docs/PROJECT_HANDOFF.md#current-state).

The downloaded files are kept outside the repository (`PACE_HALF_DIR`, default `~/data/half-1133`). `download_half.py` fetches and checks them anonymously; `half_links_extract.py` cuts `links-slim.sqlite` (medium and high links of people in both databases, person keys hashed, no names) from the links release, from its SQLite or its parquet form alike; `half_quality.py` holds the reviewed policy (`REVIEWED_HALF_POLICIES`: record rules R1–R7, edition rules E0–E8, the stamp correction, `use_sex`, date suspects, the same-city labels; the reviewed lists, the 72 withdrawn and six weaker-source stamps in `half_policy_lists.py`) and freezes it as `half-policy-20261029-1133.json` with `--write-policy`; `half_marathon.py` reads the marathon side from the public runner shards and the weather evidence; `half_pairs.py` builds set B (nearest earlier half 21–112 days before each eligible marathon, one pair per person and marathon); `half_field.py`, `half_women.py` (its band medians only from at least 20 editions; with fewer they are left out), `half_linked.py` and `half_cards.py` write the families; `build_half.py` checks the sources and the corrected metadata against the pin, asserts every count and writes `manifest.json`. Run them with `python3 -I` (DuckDB `PACE_HALF_DUCKDB_THREADS`, default 2; `PACE_HALF_DUCKDB_MEMORY`, default 4GB; spill to `TMPDIR`):

```
python3 -I analysis/download_half.py [--out DIR] [--only half|links|correction] [--from-dir DIR ...] [--links-work DIR] [--keep-links-sqlite] [--replace]
python3 -I analysis/half_links_extract.py --links-sqlite FILE | --links-parquet DIR [--out FILE] [--pin]
python3 -I analysis/half_quality.py --write-policy | --check --half FILE [--corrected-meta FILE]
python3 -I analysis/build_half.py [--half FILE] [--links FILE] [--corrected-meta FILE] [--out DIR] [--accept-counts]
python3 -I -m unittest discover -s analysis -p 'test_half.py'   # PACE_HALF_SOURCE_TESTS=1 also recomputes the frozen lists and stamps
npm run verify:half-source                                      # the local Node recount; writes docs/evidence/half/source-recount.json
```

`download_half.py` asks only `https://github.com/<repository>/releases/download/<tag>/<asset>`, with no token, cookie or `Authorization` header (never api.github.com). `--out` defaults to `$PACE_HALF_DIR` and is refused inside the repository; `--from-dir` (once per folder) takes folders already filled from the releases with their `SHA256SUMS` instead of downloading; `--only` fetches one of the three sources; `--replace` replaces a file already in `--out` (a file already there with the pinned digest is otherwise kept). It requires each release's `SHA256SUMS` to list every pinned asset with its pinned digest, checks each download as it streams, reassembles and checks the SQLite (`PRAGMA integrity_check` and the pinned digest), cuts the links extract (the 5.3 GB links SQLite can go on another disk with `--links-work`, and is deleted afterwards unless `--keep-links-sqlite`) and puts the corrected metadata in `$PACE_HALF_DIR/<its tag>/`; about 10 GB of free disk at the peak. A build takes about 2 minutes and two builds give the same bytes; it writes no temp file over 1 GB and removes its own. A count that differs from the reviewed one fails the build (`--accept-counts` only for a reviewed refresh); a new snapshot or corrected metadata fails until its lists are reviewed. `half_cards.py` writes the plots of the "From the half" cards, whose words are `lib/charts/text/half.ts` and whose images `node scripts/build-chart-cards.cjs --set half` draws while each card's guard holds. The nuggets are `lib/nuggets/half.ts`, recounted by `scripts/nuggets/half.cjs`.

`scripts/verify-half.cjs` (in `npm run verify:data`) recounts the half-only values from the published aggregates and the marathon side from the public shards, checks the linked aggregates for consistency and fails unless the receipt of the independent Node recount (`scripts/verify-half-source.cjs`, about 90 s and 1 GB) binds the current manifest and recount scripts: after any rebuild, or any change to the recount, run `npm run verify:half-source` and commit the new receipt. The **Half marathon** workflow's `source` job downloads the public sources and rebuilds and recounts in CI when the pin, policy, builders, downloader or recount change. The contract and dated evidence are in [half marathons](../docs/HALF_MARATHON.md); the refresh steps in [operations](../docs/OPERATIONS.md#half-refresh).

## Public name search and selected-race analysis

`build_public_explorer.py` shares the timing parser, canonical-ID audit, identity checks and reviewed edition exclusions with the existing builders. It writes `study/evidence.json` and `runners/manifest.json` plus deterministic gzip JSON shards. `import_public_explorer.py` invokes the full Node verifier before replacing only these two folders and current `live.json` compatibility metadata. Node must be on PATH. The **Public runner explorer** workflow rebuilds these outputs and uploads `public-runner-explorer`; it does not import or deploy them.

Names are normalized identically in Python and JavaScript (NFKD, remove Unicode marks, lowercase, retain letters/numbers, collapse spaces). Each name token contributes its first three Unicode codepoints to a SHA-256 bucket; shorter tokens use the whole token. A query loads one bucket and requires every query token to match. Results paginate without silently dropping matches. Profile buckets use SHA-256 of the candidate profile ID. Browser requests verify compressed bytes, checksum and source tag before decoding ordinary gzip, which is compression rather than encryption.

A profile is a supplied non-ambiguous identity passing the same consistency checks as linked analyses, or a singleton raw record otherwise. Matching names never merge records. Users explicitly select races, including across separate candidate groups, then confirm analysis. Every raw record is retained, including those with missing names or invalid timings; unnamed records cannot be found by a name query. Excluded records retain raw checkpoint strings and a reason. Profile IDs are release-specific and must not be treated as permanent person IDs.

Individual comparisons use only selected eligible finishes. Early pace covers 5–20 km, late pace 30 km–finish, and the opening is 0–5 km; section plots retain the actual nine timing intervals. Finish progression compares recorded years, without inventing within-year chronology. Neither the fastest selected finish nor a source identity is a verified lifetime best/person. Browser and publication tests verify unambiguous unit conversion, exclusion behavior, query handling and shard integrity.

Threshold comparisons in the supporting study allow a ratio tolerance of 1e−12 solely for binary rounding. Exact decimal boundaries are included; values 1e−9 below a boundary remain excluded. Detection, onset and the independent runner-data recount use the same convention ([conventions](#independent-verification-conventions)).

## Same-edition peers and environmental context

`build_runner_context.py` invokes the shared eligible-cohort calculation, `runner_peers.py` and `runner_environment.py`. It verifies the FULL archive/manifest and four used Parquet members, then requires the source, cohort, policy and ordered editions to agree with the exact runner manifest. The output is a context manifest plus one deterministic gzip JSON shard for each raw edition (298 in 1050, 287 in 1652). It requires a reviewed release policy; 1107, 0934, 1652 and 1050 are explicitly supported. The [complete contracts and coverage](../docs/RUNNER_CONTEXT_AND_PEERS.md) document calculation and publication evidence separately.

Peer groups are exact city/year/race, with All, recorded Men/Women, exact-age bands and combined demographics. Each group and achieved-time pacing cell requires 101 finishes. Finish distributions preserve times to milliseconds; finish percentiles exclude the selected record and give other ties half weight. Group medians and pace quartiles include the selected record. Pace bands are half-open 15-minute intervals centered on the nearest 15-minute finish, not pre-race ability or declared goals. Late change compares 30 km–finish pace against 5–20 km pace. Between-race section differences add to the signed finish difference without weather, terrain or fitness correction.

Weather joins one valid city/year row to the matching race name and verifies five exact archive hours, units and provenance. Missing/invalid fields remain absent with reasons. Terrain requires one matching supplied course and nine consistent sections; it keeps independent gain/loss/net sums, separate whole-profile totals/distances and unknown historical validity. The 1050 context covers all 298 weather editions (Chicago 2025 through the reviewed early hour in `build_weather.py` `ACCEPTED_EARLY_HOURS`, October 22, 2026) and 281 terrain editions (0934: 249 and 254). It does not fit a new weather model, infer personal exposure or adjust finish times.

Build it after importing the runner lookup, into a fresh output directory, then check and import it ([commands](../docs/OPERATIONS.md#runner-context-refresh)). The importer requires Node on PATH and runs the full independent verifier before replacing only `public/data/runner-context`. `--output` optionally selects its parent directory and defaults to `public/data`; it does not redirect the verifier's reference runner dataset. Refreshing the lookup requires a context rebuild even at the same tag because the runner-manifest hash/timestamp is part of the contract. The **Runner context and peers** workflow uploads `runner-context` without importing or deploying. Full `npm run verify:data` includes every CDF recount, 16 independent pacing-quartile samples, client tests and UI checks; finish with `npm run build` and separate production verification.
