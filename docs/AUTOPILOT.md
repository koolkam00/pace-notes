# Autopilot

The autopilot is how Pace Notes improves itself between your own changes. Twice a week a scheduled Claude session reads the site's analytics, picks one change, builds it on a branch and opens a pull request. A GitHub Actions workflow on `main` decides whether that pull request merges, waits for the deploy, checks the live site and reverts the merge by itself if the live site is broken. The data, the release pins and the privacy code are out of its reach: a guard rejects any autopilot pull request that touches them.

The rules the autopilot follows are in `autopilot/CONSTITUTION.md`. This page explains the machinery that enforces them, and what it cannot enforce.

**State on October 15, 2026.** Repository: the guard, merge gate, smoke test, statistics helper, version stamp and both workflows are in the setup pull request (branch `setup/autopilot`, rebased on `main` after the older-Safari fix, #56). Deployed: **not yet deployed or active.** Nothing merges until that pull request is on `main`, the `privacy-e2e` check and the `playwright` dev dependency exist (both come with the visit-signals pull request), and the scheduled session is turned on.

## What runs when

| What | When | Where |
| --- | --- | --- |
| **Pace Notes autopilot** (Claude session) | Mondays and Thursdays at 7:56 a.m. US Eastern | A scheduled task in Claude. It reads PostHog, writes a run note on the "Autopilot log" issue, and opens at most one pull request. It is told never to merge; see [What the machinery cannot stop](#what-the-machinery-cannot-stop). |
| **Autopilot merge** workflow | Every 15 minutes, whenever "Website data validation" finishes, and when an autopilot pull request is labelled, unlabelled, marked ready, reopened or gets new commits | `.github/workflows/autopilot-merge.yml`, always from `main` |
| **Autopilot guard** workflow | On every pull request (other branches pass at once) | `.github/workflows/autopilot-guard.yml`; early feedback only, because it runs the pull request's own copy |
| **Website data validation** | On every pull request and push to `main`, as before | `.github/workflows/site-validation.yml`; its `verify` job now also self-tests the autopilot scripts |

GitHub can start scheduled workflows a few minutes late, and turns them off after 60 days without any activity in the repository.

The merge workflow has five jobs. The two that open pages in a browser, and so run the pull request's own JavaScript (its preview) or the merged code (production), run on machines of their own with a read-only token and no credentials on disk. The gate and merge jobs check out only `scripts/` and fetch file contents as git needs them, since they read git objects, not the site. Their reads of the GitHub API are tried up to three times, so one bad answer does not fail a scheduled run.

1. **gate** checks every gate below and picks at most one pull request;
2. **preview** smoke-tests every sitemap page of that pull request's Vercel preview and runs `verify:seo:live` against it, then smoke-tests every production sitemap page as a baseline (read-only);
3. **merge** records the result on the pull request, checks every gate again and squash-merges, then waits for the production deploy. It never runs in a cancelled run;
4. **live** smoke-tests every sitemap page of https://splithappens.run, runs `verify:seo:live`, then reads `version.json` once more (read-only);
5. **report** records that the live checks passed, or opens an incident (reverting the merge when a live check failed), and then, whatever happened, makes sure every autopilot merge is accounted for.

## The loop

1. **Observe.** The session reads PostHog (aggregate numbers and a bounded number of recording summaries) and the ledger of earlier changes.
2. **Evaluate.** Changes whose evaluation date has passed are judged by the rule written down before they shipped, with `npm run autopilot:stats`. Small samples are called inconclusive.
3. **Choose.** One change, with a hypothesis, a primary metric and guardrails (names from `autopilot/metrics.md` §1), a baseline and a decision rule, appended as a line to `autopilot/ledger.jsonl` in the same pull request.
4. **Build.** On a branch `autopilot/YYYY-MM-DD-<slug>`. Before it marks the pull request ready the session runs `npm run autopilot:quick` (and pushes the draft as soon as it passes, so CI's full checks run while it works), looks at the changed pages at phone and desktop widths, and has the change reviewed against the constitution.
5. **Pull request.** Labelled `autopilot`, opened by `koolkam00` (Claude sessions act as that account).
6. **Gates.** The merge workflow checks every gate below on the current head commit, including a `verify:seo:live` run against production, so the change is never blamed for a problem the live site already had.
7. **Preview checks.** The smoke test runs over every page in the pull request's Vercel preview (with `version.json` naming the head commit), and `verify:seo:live` checks the preview's redirects, sitemap, headers and share card. Then the full smoke test runs on production, with the same coverage as the post-deploy run, as a baseline for step 11.
8. **Merge.** A squash merge, pinned to the commit that passed. The merge comment repeats the gate table.
9. **Deploy.** The workflow waits (up to 30 minutes) for Vercel's Production deployment of the merge commit, then until https://splithappens.run/version.json names that commit (up to 5 minutes).
10. **Live check.** The smoke test runs over every page in the sitemap, and `npm run verify:seo:live` checks redirects, the sitemap and headers. The smoke test reads `version.json` before the pages and again after them; if production serves another commit at either reading (another deploy replaced the merge), the run "could not finish" whatever its pages showed, since a failure may be the other commit's. `verify:seo:live` runs after the smoke test's last reading, so the job then reads `version.json` once more (`npm run autopilot:smoke -- --base https://splithappens.run --expect-sha <merge> --version-only`, with the same retries: exit 0 when it names the merge commit, 3 when it names another commit or cannot be read).
11. **Record or revert.** If both pass, the workflow leaves a hidden "live checks passed" record on the pull request. If a live check failed, it reverts the merge on `main` and opens an incident issue, which pauses everything (see [Incidents](#incidents)). The report job compares the baseline and live failure sets, matching the page, viewport, browser mode and exact failure message. It skips the revert only when every live smoke failure was already recorded before the merge; any new failure still reverts, even if another page was already broken. Missing or malformed artifacts cannot justify skipping the revert of a smoke failure. A failed SEO check reverts, because SEO passed just before merging, but only when that last `version.json` reading, after the SEO check, still names the merge commit. If it names another commit, cannot be read or is missing, production changed or could not be confirmed after the SEO check, the failure may be another commit's, and the incident opens without a revert (a smoke failure in the same run is still judged on its own, as above). If both checks pass but that last reading does not name the merge commit, the SEO check may have run against another commit, so the live result is unconfirmed: it is not recorded as passed, and the incident opens without a revert (nothing shows the change broken). A further exception is a smoke test that could not finish (exit 3): `verify:seo:live` runs right after it, so its failure counts against the change only when the smoke test's report is there, reads as JSON, comes from production and names the merge commit at both `version.json` readings, before and after the pages. Otherwise (production served another commit, or the report is missing, unreadable or lacks a reading) nothing shows the SEO check saw the merge, and the incident opens without a revert.

## Merge gates

Every gate is checked on each run, for every open autopilot pull request: one whose branch starts with `autopilot/` (in this repository or a fork) or that has the `autopilot` label. Only one may be open at a time. While two or more are open, none of them merges, and the workflow merges at most one per run. The table on the pull request's status comment (marked `<!-- autopilot-merge-status -->`, edited in place, only when something changes) is how the session learns why a pull request is waiting. Failures it has already recorded for the head commit (the preview checks failed, or GitHub refused the merge) stay on that comment, with the details and a link to the run, until a new commit is pushed.

| Gate | Passes when |
| --- | --- |
| Open, ready, targets `main` | The pull request is open, not a draft, and its base is `main`. |
| No forks | The branch is in `koolkam00/pace-notes`. |
| Autopilot branch | The branch name starts with `autopilot/`. |
| Author | Opened by `koolkam00`. |
| Label | It has the `autopilot` label. |
| No blocking label | None of `autopilot:paused`, `autopilot:needs-owner`, `do-not-merge` on the pull request. |
| Not paused | No open issue or pull request anywhere in the repository has the `autopilot:paused` label. |
| One open autopilot pull request | No other autopilot pull request is open (a branch starting `autopilot/`, from this repository or a fork, with or without the label, or any pull request with the `autopilot` label). While two or more are open, every one of them fails this gate, its table names the others, and the run's summary says nothing merges. Close all but one. If the open pull requests cannot all be listed (more than 30 pages of 100), the run fails and nothing merges. |
| Not switched off | The repository variable `AUTOPILOT_MERGE` is unset or `on`. Any other value (`off`, `false`, `0`, `no`, `paused`, …) stops merges, and the table shows the value it found. |
| Merge history | Every autopilot pull request merged in the last 14 days has either the "live checks passed" record or an incident issue. One that has neither (merged by hand, or by a run that was cancelled or timed out before the live checks) gets an incident issue at once, which pauses everything. |
| Checks | The `verify` and `privacy-e2e` runs from GitHub Actions are there and their latest attempt succeeded. Skipped or neutral fails, because the check never passed (for example a job whose condition was false). Every other check run on the current head commit finished cleanly: for each app and name, the latest attempt completed with success, neutral or skipped. Anything queued or running waits; any other result fails. A check on an older commit does not count. |
| Vercel status | The `Vercel` commit status on the head commit, posted by `vercel[bot]`, is success. |
| Guard | `main`'s copy of `scripts/autopilot-guard.cjs` passes on the pull request's head (see below). |
| Review threads | No unresolved review thread. |
| Change requests | No reviewer's latest review requests changes (the Codex review bot can request changes; you cannot on a pull request opened as your own account). |
| Ready long enough | At least 15 minutes since the later of: the pull request being marked ready (or opened, if it was opened ready), and the head commit arriving (the first check suite GitHub created for it; commit dates are not used, since anyone can set them). |
| Mergeable | GitHub says it merges cleanly, and it is not behind `main` (otherwise the table says "needs main merged in"). |
| Preview | `vercel[bot]` reports a successful Preview deployment of the head commit, at one of this project's preview addresses (`htw-live-study-…-koolkam00s-projects.vercel.app`). |
| Preview checks have not failed | The preview checks (next row) have not already failed on this commit. Push a fix, or an empty commit, to try again. |
| GitHub has not refused | An earlier merge attempt on this commit was not refused by GitHub (for example by a ruleset); the reason is in the table. Push a commit to try again. |
| Live site healthy | `verify:seo:live` passes against production just before merging. Checked only once everything else passes; while it fails, merges wait (the table says what fails), so the change is not reverted for a problem it did not cause. |
| Preview checks | After the gates: the smoke test of every sitemap page passes on the preview, including `version.json` naming the head commit, and `verify:seo:live` passes against the preview. A failure blocks that commit. If the checks could not finish (the browser did not start, or the preview could not be reached), the commit is tried again on the next run. The full smoke test of production that follows is a baseline only: it never blocks the merge (so a change that fixes a problem on production can ship), but its individual failure identities determine whether a later smoke failure is pre-existing. An aggregate failed exit code never exempts new failures. |

## What an autopilot pull request can never change

The guard (`npm run autopilot:guard -- --base origin/main --head HEAD`) reads the change with git only and never runs code from the pull request. It fails the pull request when:

- **It touches a protected path** (added, changed, deleted or renamed). The authoritative list is `PROTECTED` at the top of `scripts/autopilot-guard.cjs`:
  - data and releases: `analysis/**`, `public/data/**`, `data/**`, `docs/evidence/**`;
  - privacy and measurement, **under every file extension** (webpack prefers a `.js` or `.mjs` file to a `.ts` file of the same name, so a sibling would replace the module): `lib/analytics.*`, `lib/analytics-policy.*`, `lib/replay-policy.*`, `lib/event-policy.*`, `lib/data-fetch.*`, `lib/experiment-runtime.*`, `lib/chunk-reload.*`, `components/SiteAnalytics.*`, `components/AnalyticsPreference.*`, `components/PageFeedback.*`, `components/SectionTracker.*`, every `components/Experiment*` file (the experiment framework, including `ExperimentVariant.tsx` with `useVariant`; the registry `lib/experiments.ts` stays open), `app/privacy/**`, `docs/ANALYTICS.md`;
  - error pages, at any depth: `app/**/error.*`, `app/**/global-error.*`, `app/**/not-found.*` (the smoke test recognises an error page by `main`'s headings, so a new one would hide crashes from it);
  - checks and tooling: `scripts/**`, `.github/**`, `.claude/**`, `package.json` (in any folder), `package-lock.json`, `next.config.*`, `vercel.json`, `tsconfig.json`, `.gitignore`, `.npmrc`, `.nvmrc`, `.node-version`;
  - rules and the documents that describe them: `CLAUDE.md`, `AGENTS.md`, `autopilot/CONSTITUTION.md`, `autopilot/metrics.md`, `docs/AUTOPILOT.md`, `docs/PROJECT_HANDOFF.md`, `LICENSE*`.
- **It touches anything outside the allowed areas.** An autopilot pull request may only change `app/`, `components/`, `lib/`, `hooks/`, `context/`, `public/` (not `public/data/`), `styles/`, Markdown files under `docs/`, and `autopilot/ledger.jsonl`, `autopilot/backlog.md` and `autopilot/LEARNINGS.md`. Every file at the root, every dotfile in any folder (`.env.production`, `.babelrc`, `.postcssrc`, `.vercelignore`, …) and any new top-level folder counts as protected, because Next.js and Vercel read such files at build time.
- **It adds JavaScript to site code**: a new or renamed `.js`, `.jsx`, `.mjs` or `.cjs` file under `app/`, `components/`, `lib/`, `hooks/`, `context/` or `styles/`. Site code is TypeScript; JavaScript is not type-checked and would win over a TypeScript module of the same name.
- **It deletes or moves a page**: any `app/**/page.tsx` or `app/**/route.ts`, and the files behind `/robots.txt`, `/sitemap.xml` and the web manifest. URLs are your decision.
- **The root layout loses analytics**: `app/layout.tsx` must still render `<SiteAnalytics />` (and `<ExperimentHead />` once `main` has it). This is a pattern check: commented-out tags (including trailing `//` comments) and tags behind `false &&` do not count, but it cannot prove the component renders.
- **An added line could leak data, load something from elsewhere or replace error UI**: `<script`, `next/script`, `dangerouslySetInnerHTML`, `innerHTML` and similar, `eval(`, `new Function(`, cookies, `localStorage`, `sessionStorage`, `indexedDB`, `sendBeacon`, `XMLHttpRequest`, WebSockets, `EventSource`, any mention of PostHog, `<iframe>`, `<embed>`, `<object>`, `<base>`, `javascript:` addresses, `fetch(` or `import(` of an absolute address, `src=`, `srcSet=` (any candidate), `url(`, `@import` or `<link href=` pointing at another host, inline event handlers (`onload=`, `onerror=`) in HTML and SVG files, and a custom error boundary (`getDerivedStateFromError`, `componentDidCatch`). In `.ts`, `.tsx` and `.js` files the tags and `url(` are matched in lower case only, so React components such as `<Link>` or `<Frame>` and the `URL` constructor are not mistaken for them; `<object` followed by type punctuation (`Array<object>`) is a type, and `javascript:` counts only as an address (after a quote, `(` or `=`), so copy such as "needs JavaScript: …" is fine.
- **An added line names another host outside a link.** Any address on another host in code (a constant, a data list, a template, a `setAttribute` call, page metadata) fails, because a later line can load it and external images, fonts, scripts and data reveal visitors' IP addresses. So does an address whose host is computed (`` `https://${host}/…` ``, `'https://' + host`), which the guard cannot read. A link's address is fine where a link's address belongs: `href=` (an `<a>` or a `next/link` `<Link>`) or a `url`, `href` or `link` field of a list of links, as the citations already use. Identifiers that are never fetched are fine too: XML namespaces (`xmlns:inkscape="http://…"`) and the JSON-LD fields `license`, `sameAs`, `citation` and `@id` (`npm run verify:seo` keeps the JSON-LD privacy rules). Addresses on the site itself, `doi.org`, `schema.org`, `www.w3.org`, `www.sitemaps.org` and `github.com/koolkam00` are allowed anywhere, and addresses in comments are ignored (a comment marker inside a string does not count as one).
- **An added line breaks a copy rule**: the banned words and phrases in constitution §3 ("the wall clock" is fine), and the release identifiers that never appear in visible copy (the tag, not the `private-export-` prefix the data loaders use to check a release).
- These scans cover every changed file except the prose files (Markdown under `docs/`, and the three `autopilot/` files). A file moved into site code from a path that was never scanned is read in full, not just its changed lines. A line moved unchanged from one scanned file to another (a component split in two) is existing code and is not reported again; an edited line is. Nor is a line a revert puts back: when the pull request moves a ledger entry to `reverted` with verdict `revert`, each line that entry's merge commit deleted from a file (the commit the `shipped_on` check finds; all of a file it deleted or renamed away) may come back to that same file unchanged, as often as it was deleted, since it was on `main` before that merge. This is how the skill's revert pull request puts back owner code the autopilot could not add itself, such as browser storage or an address on another host.
- **It is too big**: more than 60 changed files; more than 1,500 changed lines (added plus deleted, not counting the ledger); more than 200 KB of added text in one file or 1 MB in all; a line over 3,000 characters outside `public/` (no minified code or inlined images); more than 10 new ledger lines.
- **A file is not what it says**: only `png`, `jpg`, `jpeg`, `webp`, `avif`, `gif`, `ico`, `woff`, `woff2`, `ttf`, `otf`, `pdf`, `mp4` and `webm` files may be binary, only under `public/` (not `public/data/`) or as a Next.js icon or share image under `app/` (`favicon.ico`, `icon`, `apple-icon`, `opengraph-image`, `twitter-image`), each at most 600 KB and 2 MB in all. Every other file must be UTF-8 text, so it is scanned. Symbolic links and submodules are refused.
- **The ledger is wrong** (the schema, field by field for each kind, and the lifecycle are in `autopilot/metrics.md` §4; the guard's copy is `LEDGER_SCHEMA`): the pull request must append at least one line to `autopilot/ledger.jsonl`, unless it is a bookkeeping pull request that changes nothing but existing ledger lines, `autopilot/backlog.md` and `autopilot/LEARNINGS.md` (it may append the records of pull requests that closed unmerged). Every new, changed or repaired line must be one JSON object on one line with `id` (unique, `YYYY-MM-DD-slug`; a new or repaired line never takes an id another line uses), `date`, `kind` (`change`, `experiment`, `conclude`, `revert`, `fix`), `title`, `hypothesis`, `primary_metric`, `guardrails` (a list), `baseline` (an object), `decision_rule`, `evaluate_after` (a date; `null` only for `fix`, `revert` and `conclude`), `status` (`proposed`, `shipped`, `reverted`, `concluded`), `pr` (a number or `null`), `verdict` (`null`, or one its kind can reach: `keep`, `revert`, `inconclusive` or `iterate` for a `change`; `ship-variant`, `keep-control`, `inconclusive` or `revert` for an `experiment`; `keep`, `revert` or `inconclusive` for the others) and `result` (`null` or a non-empty object); `shipped_on` and `evaluated_on`, when present, are dates or `null`, and `notes` is text. `title` cannot be blank (empty or only spaces), nor can a new entry's `hypothesis` and `decision_rule`. Everything the evaluation later reads is registered with the entry and never changes:
  - **What a change or experiment registers.** `min_sample` (a positive safe integer: the fewest visits each before/after window, or each experiment arm, needs); a measured `baseline` with `window` (`"YYYY-MM-DD..YYYY-MM-DD"`, 7 to 56 whole UTC days counting both ends, ending on or before the entry's date), `visits` or `n` (a positive whole number; the same, if both are given) and any other numbers non-negative and finite; at least one guardrail. A `change` also registers `window_days` (14 or 28, the length of each before/after window), and its `evaluate_after` is 14 to 90 days after its date and at least `window_days`. An `experiment` registers `max_days` (an integer from 1 to 42), its registry `experiment` key and canonical `pages` (with an optional `area`), and its `evaluate_after`, its planned end, is 7 days (or `max_days`, if shorter) to `max_days` + 1 day after its date (a later ship moves the due date instead). The pull request that registers an experiment also sets its registry `started` (required: on or after the entry's date and not after today, a day of slack aside), `variants` and `weights` (below). Only a change has `window_days` and only an experiment `max_days`. A `fix`, `revert` or `conclude` needs no `min_sample`, may record any object as its `baseline`, and has `evaluate_after` null: nothing registers windows or a sample to judge it on.
  - **Dates happen in order.** "Today" is the head commit's UTC day, or the clock's if that is earlier (anyone can set a commit's date). `shipped_on` is never before the entry's date, `evaluated_on` never before the date or `shipped_on`, and neither is more than a day after today; a new entry's date is not after today either, so the day it ships can never come before it. When `shipped_on` is set on a line already on `main`, it must be the UTC day of the first first-parent commit on the base whose ledger has that line (its pull request's merge, the day the automatic revert records too); if the history cannot show that commit (a shallow clone), the guard fails and says to fetch it. The evaluation is due on the later of `evaluate_after` and the end of the entry's windows (a change's counted from `shipped_on`; an experiment's from its start, `shipped_on` or the registry's `started` if later; `autopilot/metrics.md` §4), so a late ship is never judged on too little data. The guard refuses a `change` concluded before its due date (its `evaluated_on`, and today, are on or after it), and a shipped `change` given verdict `inconclusive` as it moves to `reverted` before it: an early look would take a live change out of its evaluation (and a bad one out of the streak check). An experiment's stopping rule may decide it sooner, and any entry may be rolled back sooner (status `reverted`, verdict `revert`).
  - A **new** entry is pre-registered: status `proposed`, `verdict`, `result` and `shipped_on` null, dated within two days of the branch date (and not after its commit), with `id` exactly equal to the branch name after `autopilot/`, and naming this pull request or none. The one exception is the record of an earlier change whose pull request closed without merging: status `reverted`, with `verdict` null or `inconclusive`, its earlier date and historical branch ID, `shipped_on`, `result` and `evaluated_on` null (it never shipped, so it was never evaluated), and its provenance, which it must have: `pr`, the number of the pull request that closed, and a non-empty `notes` saying why it closed. Such a closed-unmerged record cannot substitute for the new proposal required by a site-changing pull request.
  - An **existing** entry cannot be removed or moved, and only `status`, `verdict`, `result`, `evaluated_on`, `pr`, `shipped_on` and `notes` may change. The status only moves forward (`proposed` to `shipped`, `concluded` or `reverted`; `shipped` to `concluded` or `reverted`; `concluded` to `reverted`), and `verdict`, `result`, `evaluated_on`, `pr` and `shipped_on` may be filled in once and are then fixed. A `reverted` entry without `shipped_on` (a closed-unmerged record) never gains one, nor a `result` or `evaluated_on`: no merge of its own exists to check a ship day against, and the day its record reached `main` is a bookkeeping merge's. Lines are matched by `id`, so a deleted line is reported as deleted.
  - A **proposed** entry has `shipped_on`, `verdict`, `result` and `evaluated_on` null, so bookkeeping can mark it shipped. A **shipped** entry requires non-null `pr` and `shipped_on`, and still has `verdict`, `result` and `evaluated_on` null, since the evaluation picks shipped entries whose verdict is null. A **concluded** entry also requires non-null `verdict` (never `revert`: an entry with a `revert` verdict moves to `reverted` in the pull request that reverts the change, and stays `shipped` with verdict null until then), `result` and `evaluated_on`; it cannot leave the evaluation queue without its outcome. An existing entry that moves to **reverted** leaves the queue too, so it needs verdict `revert` or `inconclusive`, its `pr` and a note saying why (the note it already had does not count); with verdict `revert` it also needs `shipped_on` and `evaluated_on`, and a shipped `change` judged before its due date takes verdict `revert` (above). The automatic revert writes all of these. A `reverted` entry without `shipped_on` never shipped, so its `result` and `evaluated_on` stay null too. A new closed-unmerged record keeps its own rule (above).
  - **Metric names.** In a new entry, `primary_metric` and every item of `guardrails` must be a metric name from the `## 1. Definitions` table of `autopilot/metrics.md`, written exactly as there, version included (`answered_visit_rate@v1`). A `change` or `experiment` needs at least one guardrail; `fix`, `revert` and `conclude` may have none. The guard reads the table from `main`, so a pull request cannot add a name for itself. If the file is missing or its table defines no names, every new entry fails, and so does a repaired one (below). Unknown names on lines already on `main` are warnings.
  - Problems already on `main` (a blank line, a byte-order mark, two lines sharing an id, an old entry that breaks a rule) are reported as warnings, so they never block every later pull request. An old line that breaks a rule about a field that never changes, because the rule is newer than the line or the owner wrote it so (a `change` without `min_sample` or `window_days`, an experiment without `min_sample` or `max_days`, a blank hypothesis or decision rule, an unmeasured baseline, an `evaluate_after` that is missing or out of range, a `shipped_on` before its date, a verdict its kind cannot reach, a conclusion before its due date, and the like), also only warns when a pull request ships, concludes or reverts it, since those fields can never be filled in or changed. A broken line may be repaired. If it parsed on `main` before (a hand edit broke it later), it is held to that version, found by the id its broken text names, else the repaired line's, as an edited line is to its base copy: only the mutable fields change, the status only moves forward, and a `shipped_on` it gains is the day of the commit that put the line on `main`. If it never parsed there, it meets the whole schema, its metric names included, as a new entry does, and a `shipped_on` it gains is the day its broken text reached `main`. Either way it takes an id no other line uses.
- **Experiments compete or cannot be inspected.** When an experiment is proposed or the registry changes, the guard counts the union of `proposed`/`shipped` experiment ledger entries and `running` registry entries, matching by experiment key. At most two may occupy slots, and their page areas cannot overlap. Active ledger experiments require `experiment` (the registry key) and nonempty, unique canonical `pages`; optional `area` is a lower-case slug, and omitting it reserves the whole page. `"*"` reserves all pages or all areas. Concluding a ledger entry does not free a slot while its registry entry still runs. Whenever the registry or the ledger changes, every running key is compared with its registration, the latest `experiment` entry naming that key, whatever its status (other kinds and closed-unmerged records do not count): a running key whose pages or area differ from it fails ("register a new experiment instead"), and a mismatch already on `main` is a warning. A key's run, its registry `started`, `variants` and `weights`, is set by the pull request that registers its experiment (`started` is required, on or after the entry's date and not after today, a day of slack aside; the experiment framework refuses an entry without it too) and is then fixed while that registration is the latest for the key, whether the key runs or is paused (an experiment entry repaired from a broken line on `main` is on `main` already, so it keeps `main`'s run): the readout counts from the start and compares the arms, so moving them later would choose the window or the arms after seeing the data. The key may be removed, but not added again under the same registration. A newly running registry key requires an active pre-registration. A pull request that stops a running key (pauses or removes it) cannot also start one (add a running key or resume a paused one; giving a running key a new run counts as both), because the automatic revert keeps `main`'s registry only after a merge that stopped experiments and started none (below), so it could not undo both: conclude in one pull request and start the next experiment in another. Missing or uninspectable occupancy fails closed for new experiments, while ordinary changes and bookkeeping can proceed without a registry. See the data-only registry contract in `autopilot/metrics.md` §4. Alternate `lib/experiments.*` implementations and directory indexes are protected, and the registry file cannot be removed; pause or remove its entries instead.
- **The work is not committed.** Run on `HEAD` (as `npm run autopilot:check` does), the guard fails while tracked files have uncommitted changes, because it reads commits, not the working tree; untracked files are a warning.

Branch names must look like `autopilot/2026-10-15-home-hero` (a real date, lower case, at most 80 characters).

The guard is a pattern check, not a proof. It is one layer next to the constitution, CI, the adversarial review, the preview checks and the live check. A determined attempt to hide a third-party request in code it cannot recognise (for example by building a host name from pieces held in different variables) would get past it; the smoke test's network tripwire, which scrolls every page to the bottom so lazy images load too, is the next layer (on the preview for every sitemap page before the merge, and on production after it), and you can review any merged change in the pull request.

Two checks that `npm run autopilot:check` runs (and CI's `privacy-e2e` check) keep their cases in `scripts/`, so some changes need you: a new tool needs its typed-value privacy case in S2 (`scripts/e2e/scenarios/s2-differential.cjs`) and its entry in `scripts/verify-tools.cjs`, and a page whose initial JavaScript grows more than 1.5 KB past its figure in `scripts/e2e/budget.json` needs a new figure (S8, `--only=S8 --write-budget`). A new page route without a figure of its own is measured on one of its pages and held to the largest figure in its section (the budgeted pages sharing its first path segment; in a new section, the largest of all) + 1.5 KB, and S8 notes it so you can measure its own figure. The constitution lists these as owner-only actions.

`npm run verify:seo` also keeps two privacy rules of its own, rather than reading them from `lib/seo-routes.ts` (which autopilot pull requests may edit, for example to update a page's date): `robots.txt` must keep blocking the two folders of recorded runner names, and `/runners` and `/your-race` must stay noindex.

## How to stop it

In order of how quickly they act:

1. **Add the label `autopilot:paused` to any open issue**, for example the "Autopilot log" issue. Merges stop within 15 minutes, and the scheduled session sees the label and skips its run. The label is checked again just before merging, so it also stops a run that is already under way. Remove the label, or close the issue, to resume. (Cancelling a run of the workflow before its merge step also stops that one merge.)
2. **Set the repository variable `AUTOPILOT_MERGE` to `off`** (Settings → Secrets and variables → Actions → Variables); any value other than `on` works. Nothing merges in runs that start after the change. A run already under way may have read the old value, so use the label above when it must stop now. The session can still open pull requests.
3. **Disable the "Autopilot merge" workflow** in the Actions tab. Pull requests then stay open until you merge them yourself.
4. **Turn off the "Pace Notes autopilot" scheduled task in Claude.** No new sessions run.

To hold one pull request without pausing everything, add `autopilot:needs-owner` or `do-not-merge` to it, or leave a review comment unresolved. While it stays open, no other autopilot pull request can merge (one open at a time); close it to let the next one through. (Requesting changes does not work on these pull requests: they are opened as your own account, and GitHub does not let an author request changes on their own pull request.)

## Incidents

When a live check fails after a merge, the workflow:

1. reverts the merge commit on an up-to-date `main` as `github-actions[bot]` and pushes it (if the revert conflicts with later commits, or the push is refused, it skips the revert and says so; Vercel deploys a successful revert as usual). The revert keeps the records: the squash merge contained the change's ledger line and any learnings, so the revert commit puts `main`'s ledger and `autopilot/LEARNINGS.md` back and marks the entries that merge added `reverted` (verdict `revert`, with the pull request, `shipped_on`, `evaluated_on` set to the day of the revert, and a dated note, which is the complete record the guard requires). The ledger therefore still shows that the change was tried and reverted, which the session's "two reverts in a row" check reads. When the merge stopped an experiment (a key running before it is paused or removed after it, as a conclusion does) and started none, the revert also keeps `main`'s `lib/experiments.ts`, and a conflict there does not stop it: a concluded experiment never runs again, and no pull request could restart it (the guard requires an active registration). A merge that started or resumed a key is reverted in full, so that experiment stops with its code (the guard refuses an autopilot pull request that also stops one, so only an owner's merge could do both, and it is reverted in full too);
2. opens an issue titled `Autopilot incident: <pull request title>` with the labels `autopilot-incident` and `autopilot:paused`, saying which step failed, a short log excerpt, the workflow run, the pull request, the merge commit and whether the revert was pushed (opening the issue is tried three times);
3. comments on the pull request with a link to it.

Because the issue carries `autopilot:paused`, nothing else merges until it is closed, a revert pull request included. When the automatic revert could not be pushed and the site is still broken, the session opens a revert pull request and asks you, under "Needs you" in its log, to close the incident so that the revert can merge through the usual gates (or use a Vercel rollback for a hard outage). Other cases open the same issue without reverting, because they do not show the change itself is at fault:

- the deploy failed or timed out (the issue gives the reason: a Vercel failure, no deployment in time, or `version.json` not naming the merge);
- the live checks could not finish: the site could not be reached; production served another commit than the merge before or after the smoke test's pages (another deploy replaced it), which the smoke test reports as "could not finish" whatever its pages showed, because a failure may be the other commit's; or the job was cancelled or timed out. When the smoke test could not finish, a failed `verify:seo:live` in the same run does not revert either, unless the smoke test's report shows production serving the merge commit before and after the pages (a missing or unreadable report shows nothing). Nor does a failed `verify:seo:live` revert when `version.json`, read once more after it, names another commit, cannot be read or has no result: production changed or could not be confirmed after the SEO check. When both checks passed but that reading does not name the merge, the live result is unconfirmed, so it is not recorded as passed either: the incident opens without a revert and stays open until someone confirms the live site (`npm run verify:seo:live` and the smoke test);
- every live smoke failure exactly matches one in the full pre-merge baseline (page, viewport, browser mode and message). This opens an incident without reverting. New failures, including a different error on an already-broken page, still revert. Exact matching is intentionally conservative: changed error text or measured CLS values count as a new failure rather than risk hiding a regression. The baseline and live JSON remain in the run's artifacts;
- a merged autopilot pull request has neither the "live checks passed" record nor an incident. The workflow checks this at the end of every run and at the start of the next one, so a merge by hand, a cancelled run, a lost answer from GitHub or an incident that could not be opened all end in an incident.

The workflow does not watch the revert's own deploy; the next session (or you) confirms it with `npm run autopilot:smoke -- --base https://splithappens.run --quick` before closing the issue. The constitution allows the session to close an incident only once the cause is understood and fixed and the live smoke test passes.

Merges and reverts made with the workflow's `GITHUB_TOKEN` do not start other workflows, so "Website data validation" does not run on those pushes to `main`. The pull request's own CI run, the preview checks and the live checks stand in for it. Vercel still deploys them.

## What the machinery cannot stop

The Claude session acts as your GitHub account, `koolkam00`, which is an admin of a repository whose `main` is not protected, and it has tools that can merge pull requests and push commits. "It never merges" is an instruction in the constitution and the session's playbook, not a technical limit. What the machinery does about it:

- every gate, the guard and the merge itself run from `main`'s copy of the workflow, so an autopilot pull request cannot loosen them;
- an autopilot pull request merged by anyone but the workflow is noticed within 15 minutes and opens a paused incident, so nothing else merges until you have looked;
- a push straight to `main` is not noticed by the workflow. The Vercel deploy and your own review are the only checks on it.

A ruleset on `main` does not close this while the session uses your account: an admin can bypass rulesets, and the `autopilot-guard` check that a ruleset could require runs the pull request's own copy of the guard, so a pull request that edits it can make it pass.

## Optional hardening (owner steps)

- **Durable fix: give the session its own GitHub account** with the write role (not admin), and sign it in instead of yours. Then add a ruleset on `main` (Settings → Rules → Rulesets): require a pull request, require the `verify` and `privacy-e2e` checks, block force pushes and deletion, and restrict who may update `main` to the admin role and the merge workflow's identity. Change `allowedAuthors` in `scripts/autopilot-merge.cjs` to the new account in the same owner pull request.
- **Do not add "GitHub Actions" as a ruleset bypass actor.** It would let any workflow push to `main`, including a push-triggered workflow committed on any branch, which runs before any guard. If a ruleset blocks pushes to `main`, the automatic revert's push is refused; the incident then says "not pushed", and you revert by hand. To keep automatic reverts under a ruleset, use a dedicated GitHub App (or deploy key) whose secret lives in an environment that only `main` may use, and use it only for the revert push. This needs a small change to the workflow, made by you.
- **Pin the "Autopilot log" issue**, so its pause label is easy to find.
- **Optionally turn off the Vercel Toolbar on previews** (Vercel project settings). The smoke test already ignores it, but previews then load nothing from another host at all.
- **Create the labels** `autopilot`, `autopilot:paused`, `autopilot:needs-owner`, `autopilot-incident`, `autopilot-log` (the session finds the "Autopilot log" issue by it) and `do-not-merge` ahead of time (the workflow creates the incident and pause labels itself if they are missing).

| `npm run autopilot:check` | Everything CI checks, locally: `verify:data`, `verify:analytics`, `verify:compat` (older-browser source scan), `build`, `verify:compat -- --build`, `verify:seo`, `verify:autopilot`, `autopilot:privacy`, then the guard against `origin/main` (commit first: the guard reads commits). It takes about 25 minutes, most of it `verify:data` and the browser tests; use it, or the one command that failed, to reproduce a CI failure. |
| `npm run autopilot:privacy` | The browser privacy tests exactly as CI's `privacy-e2e` check runs them: a build with the dummy key `phc_test_dummy` (so the `out/` folder it leaves sends nothing real; PostHog refuses that key), then `npm run verify:replay-e2e` with PostHog mocked and every other host blocked. |
| `npm run autopilot:guard -- --base <ref> --head <ref> [--branch <name>] [--pr <n>] [--json]` | The guard. The branch defaults to `GITHUB_HEAD_REF`, then the checked-out branch when `--head` is `HEAD`; other branches pass without checks. `--pr` lets it check that new ledger lines name this pull request. `--self-test` builds temporary repositories covering every rule. |
| `npm run autopilot:smoke -- --base <url> [--quick] [--expect-sha <sha>] [--json <file>]` | Opens pages in Chromium at 390×844 (and 1366×900 for `/` and `/tools`), scrolling each to the bottom in steps so lazy images and anything loaded on scroll are requested too, and watching each for at least 5 seconds from the start of its navigation. Fails on a status other than 200, a page error, Next.js's "Application error" screen, a missing or hidden `<h1>`, an error page (the site's error-page heading, or any element marked `data-error-boundary`), or a request to the site itself answering 400 or more. The quick list is also opened as Safari before 16.4 behaves (a RegExp with lookbehind throws). Requests to other hosts are aborted in every browser context, the home-page lab runs included: PostHog's are counted, the lab runs' included (expected on production; nothing is sent), so is Vercel's own preview toolbar (`vercel.live`, which Vercel adds to `*.vercel.app` previews only), and any other host fails the run, with the host and the page (`/ (performance)` for a lab run). A page whose first load failed for a network reason (a timeout, a 5xx, a failed request to the site) is loaded once more and fails only if that load fails too; a page error or crash with no network cause fails at once, so an error that shows up on some loads only is not hidden. `sitemap.xml` and `version.json` are fetched up to three times. It also measures the home page with 4× CPU throttling and a 1.6 Mbps / 150 ms network and reports LCP, CLS and total blocking time; only a CLS above 0.25 fails (no finished lab run is a warning). With `--expect-sha`, `version.json` is read before the pages and again after them; with `--expect-sha` and `--version-only` it reads only `version.json`, the same way (no browser, no pages), and exits 0 when it names that commit, 3 when it names another commit or cannot be read (the live job's reading after `verify:seo:live`). Exit 0 passed, 1 failed, 3 could not finish: the browser did not start, or `sitemap.xml` or `version.json` could not be read, and nothing else failed; or a non-preview address such as production served another commit at either reading, whatever else failed (the summary says production is serving another commit). On a `*.vercel.app` preview, whose address belongs to one deployment, another commit is a failure. `--self-test` checks these exit codes and the tripwire against a stand-in browser. Behind a proxy, run it with `NODE_USE_ENV_PROXY=1`. |
| `npm run verify:seo:live` | The live search checks. Each request is tried up to three times when the network fails or the site answers 5xx; exit 3 means the only failures were requests that never got an answer. |
| `npm run autopilot:stats -- <command>` | `ab --a x/n --b x/n` and `prepost --before x/n --after x/n` (rates with 95% Wilson intervals, the difference with Newcombe's interval, a two-sided z-test and the probability that B is higher); `mde --p <rate> --n <per group>` and `need --p <rate> --lift <difference>` (80% power, two-sided 5% level); `median` and `p75 --values a,b,c`. Add `--json` for machine output. |
| `npm run verify:autopilot` | Self-tests of the guard, the merge gate (against a mocked GitHub API, including the workflow's artifact-to-decision command and real report-driven reverts in temporary repositories), the smoke test's exit codes and third-party tripwire (against a stand-in browser and site, no network), the statistics (against published values) and the JavaScript budget's rules for routes without a figure (S8, against a stand-in build). CI runs it. |
| `node scripts/autopilot-merge.cjs evaluate --dry-run [--pr <n>]` | The merge gate's view of open autopilot pull requests (or of one pull request), writing nothing. Without `GITHUB_TOKEN` it reads the public API anonymously and cannot read review threads. `reconcile --dry-run` lists autopilot merges without a live-check record. |

**Version stamp.** `npm run build` first runs `scripts/write-version.cjs`, which writes `public/version.json` with the commit (`VERCEL_GIT_COMMIT_SHA`, else git), the branch and the build time. It is ignored by git, served with `Cache-Control: no-store` and `X-Robots-Tag: noindex`, and is not in the sitemap. The merge workflow and `--expect-sha` read it to confirm which commit a preview or production deploy serves.
