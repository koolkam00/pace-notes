**Repository state:** in this change (branch `feat/visit-signals`, built on `fix/old-safari-crash`). **Deployed state:** not yet deployed. Until it is, PostHog receives none of the signals below.

What changed:
- **Signals for judging a change.** New events, all through the existing `before_send` allowlist, so each carries only enumerated values or bounded numbers: `tool_used` (`edit`, `print`, `copy_link`), `page_feedback` and `page_feedback_reason` (a "Was this useful?" row with fixed buttons at the end of stories, tools and analyses; no text box), `site_error` by kind only (`js_error`, `unhandled_rejection`, `chunk_load`, `data_fetch`, `render`; at most one per kind per page view and five per page load), `section_viewed` (the home page's hero, chapters, story list, tools, analyses and closing call), `$pageleave` with the SDK's time on page and scroll depth (also on the next `$pageview`), `$web_vitals` values (LCP, FCP, INP, CLS), result bands on `runner_search_completed`, and the fixed tags on the owner's Instagram links (`utm_source=instagram`, `utm_medium=social`, `utm_content` bio/story/highlight/reel/post/dm) on a tab's first page view; every `utm_*` is then removed from the address. Typed values, names, messages and addresses never leave.
- **Fixes.** `units_changed` is sent only on a real change; story and course pages keep their own analytics path (literal lists checked against the published stories and courses); each event carries the time the site asked for it, so the first page's time on page is not cut short.
- **Data requests.** Every browser request for the site's data goes through `lib/data-fetch.ts`, which reports a network failure or an error status as `site_error` `data_fetch` (not a request the page cancelled) and otherwise behaves like `fetch`. `verify-analytics` refuses a direct `fetch(` in client code.
- **Experiments framework.** `lib/experiments.ts` is the registry (data only; empty). `lib/experiment-runtime.ts` and `components/Experiment.tsx` give each tab one variant of each running experiment before the first paint, with no feature-flag request, keep it in sessionStorage (`pace-notes-exp:<key>`), show it with CSS (`<Variant>`), and add `$feature/<key>` to that tab's events. Paused experiments, blocked storage and no JavaScript all show the control and report nothing.
- **Privacy page and docs.** `/privacy` lists every counted action from a map that `verify-analytics` checks against the event list, and says which version of a page you were shown, when we test two designs. The events table, storage keys and experiments rules are in [analytics](ANALYTICS.md).
- **Browser privacy checks in CI.** `npm run verify:replay-e2e` (`scripts/verify-replay-e2e.cjs`, `scripts/e2e/`) drives Playwright Chromium (`playwright` 1.56.1, exact devDependency) through a dummy-key build with PostHog mocked and every other host aborted: browsing, every tool and calculator with two sets of values, the runner journey, privacy signals and blocked storage, every sitemap page in emulated old Safari, the visit signals, error pages, data failures, unload beacons and the initial JavaScript budget (`scripts/e2e/budget.json`). Every visitor is checked against the site's own allowlist and replay rules (hosts, events, recording fields, typed and runner values, blocked pages, storage, privacy signals, page errors); differences between the two value sets must be listed with a reason in `scripts/e2e/known-differences.json`. The new CI job `privacy-e2e` in `.github/workflows/site-validation.yml` builds with the dummy key and runs it; the autopilot's merge gate requires that check by name. Details and options: [analytics](ANALYTICS.md#browser-privacy-checks).

Measured (dummy-key builds, PostHog mocked so nothing left the machine): initial JavaScript +1.5 KB gzipped on `/` (+1.3 to 2.6 KB on other page types; Web Vitals add 3.9 KB to the lazily loaded SDK chunks only). Details, the browser checks and their limits are in [analytics](ANALYTICS.md#verification). Not verified: real iOS devices, `beforeprint` on iOS, `$pageleave` when a real browser tab is closed (seen when leaving for another page, and when Playwright closes the page with its unload handlers), and whether Instagram's in-app browser adds other tags. The browser privacy checks (`npm run verify:replay-e2e`) passed in full locally: 68 jobs and 92 visitors in 6 min 40 s (10 min 10 s on 2 cores), and they fail when masking is removed or a lookbehind is added; CI has not run the new `privacy-e2e` job yet. ## Older Safari fix and error pages (October 14, 2026)

**Repository state:** in this change (branch `fix/old-safari-crash`). **Deployed state:** not yet deployed. Until it is, splithappens.run still runs the code that crashed in the emulated check below.

What changed:
- **The crash.** Safari before 16.4 (iOS 15, iOS 16.0–16.3) cannot build a regular-expression lookbehind, and the miles conversion in `lib/units.ts` built five of them in code the root layout runs. With old Safari emulated in Chromium, a build of `main` showed "Application error" on 79 of the 115 sitemap pages; this change shows it on none. A crashed page sends no analytics. So PostHog's browser breakdown could not show these visitors. The conversion now works without lookbehind and gives the same output on 4,361 distinct published and source strings. The two build-time sentence splits (`/slowdown`, pack descriptions) were rewritten too.
- **Guards.** `npm run verify:compat` scans the browser source for lookbehind and for built-ins that need Safari 15.4 or later. `npm run verify:compat -- --build` scans the built JavaScript for lookbehind. CI runs both, and `verify:analytics` runs the same source scan. `verify-units` reruns its conversion table with lookbehind refused.
- **Error pages.** `app/error.tsx` (inside the site's header and footer) and `app/global-error.tsx` (when the root layout fails) replace Next.js's blank "Application error" screen. Each offers "Reload the page" and a link home, moves focus to its heading and sets the tab's title. After a failed script load, the page reloads by itself once. A sessionStorage timestamp (`pace-notes-chunk-reload`) stops it doing so again within five minutes. A small script in the root layout's `<head>` makes that reload happen at once when a script or stylesheet named in the page's HTML fails; without it webpack waits two minutes, and a failed React file never reaches an error page. A chart whose chunk fails shows a note in its box instead of the error page replacing the whole page.

Methods, measurements and limits: [website architecture](WEBSITE_ARCHITECTURE.md#older-browsers-and-error-pages). Not verified: real iOS 15/16 devices (the checks emulate old Safari in Chromium), and how many visitors were affected. Release pins and data are unchanged.

Whole-minute target support is 1:30–12:00; achieved-time profiles use 15-minute bands. A valid selection does not guarantee a sufficiently large cohort. Previous time means a band of recent recorded bests from strictly earlier years, not a verified last marathon. Terrain requires an explicit course and remains a supplied-route proxy. ## Fast-start analysis

Rank 2, `/analyses/starting-pace`, defaults to [all eligible finishes](../public/data/fast-start/all-finishers.json): **3,517,336** performances, including **2,961,899** without a recent prior benchmark. It compares first 5 km pace with the same race's 5–20 km pace using six fixed intensity bands. The primary time outcome is actual elapsed time after 20 km minus the time at that recorded reference pace; the actual median finish is separate. First-5 km and after-20 km mean differences add to the whole-race mean difference because the 5–20 km reference block contributes zero. No earlier history, cross-race identity link, speed filter or imputed data is needed.

The optional [earlier-best comparison](../public/data/fast-start/evidence.json) retains its original output byte for byte. It compares first 10 km pace with the best eligible finish in the two strictly earlier calendar years, covering **555,437 benchmarked finishes**, 576 exact filter combinations and 2,846 groups. Its history restrictions do not limit the new default mode. The earlier personalized opening/target-threshold path remains in the research guide without recalculation.

Both builders check all 7,766 compressed runner shards and source script hashes and reconcile raw/eligible counts. Both outputs bind the exact runner-manifest hash, so lookup refreshes require rebuilding both. Each displayed group needs 100 finishes. Onset distributions additionally need 100 detected finishes and use only those detected finishes as their denominator; the slowdown rate uses every finish in the selected mode/group. All raw records remain searchable/downloadable under the existing lookup contract, but incomplete or held results do not enter these aggregate outcomes.

The all-finisher comparison finds unusually quick first sections, not proven excessive effort. It can miss a runner who maintains an ambitious opening pace through 20 km before fading. The same-race baseline is measured after the opening and is shared by the opening and slowdown ratios. Neither mode estimates causal time penalties, current fitness, physiological failure or withdrawals. Counts are performances, not unique runners. `comparison=all|history` selects the mode; legacy `prior=` or `previous=` links imply history only when no explicit mode is set. Explicit All clears prior filtering.

The new calculation publishes **314 filter combinations / 1,534 groups** and passes ten new Python tests and its full independent source-data verifier. Its All-filters `fast10` group has **174,935 finishes**, **49.6% sustained slowdown**, and median time after 20 km **28:04 above the 5–20 km pace reference**. Its actual median finish is **5:45:31**. The steady group has **1,500,147 finishes**, **24.5% slowdown**, and an **8:35** median after-20 km reference difference. Among detected finishes, their most common first qualifying sections are **20–25 km** and **35–40 km**, respectively. These are pooled descriptive differences, not a personal causal penalty; CI and publication remain separate from the completed local evidence.

In **history mode only**, openings more than 10% faster than the earlier benchmark have **47.0% sustained slowdown**, versus **17.9%** for openings within 2%. Their most common first qualifying sections are 30–35 km and 35–40 km. The faster-opening group's median finish nevertheless improves on its earlier benchmark by **16:37**. These figures cannot be relabeled as all-finisher findings. Nine history calculation tests and its independent verifier passed, including counts/onsets for every cell and all numeric metrics for 36 groups across six filters. [Methods, measured findings and reproduction commands](FAST_START_ANALYSIS.md) distinguish that existing evidence from verification of the new mode. CI and production evidence for the expansion remain separate.
