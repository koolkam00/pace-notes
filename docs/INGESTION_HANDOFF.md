## Historical instruction sent to ingestion agents

> Prepare the next complete, reproducible Pace Notes export for the analysis agent. Publish full runner records, names, features, overlays, backups and supporting study documentation in **public GitHub Releases** in `koolkam00/htw-live-study`. Do not replace full records with anonymized or aggregate-only substitutes. Use ordinary unencrypted Parquet and SQLite files; gzip compression is fine. Do not password-protect archives. Anyone must be able to download and open these files without a GitHub account, invitation, token or decryption key. Releases are the preferred home for large binaries so the website remains small; there is no runner-data privacy restriction on the checkout or publication.
>
> The September 10 export's canonical result IDs have already been verified: CORE/FULL both have 3,580,279 unique non-null IDs with identical sets; comparable timings agree after converting feature minutes to seconds. Preserve that fix. The current refresh is blocked by extra archive members and missing feature columns, not lack of binary access.
>
> **1. Freeze and identify the source.** Create a consistent SQLite snapshot using SQLite's backup mechanism while leaving live ingestion intact. Run an integrity check. Record the snapshot identifier, UTC creation time, ingestion repository/commit, feature-generator repository/commit, dependency versions, exact commands and schema version. Generate every table and feature from that one snapshot, never a moving live file or mixed snapshots. Include the full corpus, all feature columns, invalid/incomplete rows and all overlays; do not send samples or filtered substitutes for the full export.
>
> **2. Restore consumer-compatible features.** Preserve `features.record_id = race_records.id`. Add the currently missing `features.race` and `features.runner_name` from that same snapshot's raw `race` and `runner` fields through the canonical ID. The existing history calculation and expanded audit require both columns. Preserve every existing feature column. Supply `split_mode_in` only with a truthful definition; never invent a missing field just to reach a historical column count. If you intentionally change field names, types or units, coordinate and validate a version-specific consumer change before release. A new ID namespace must never be applied retroactively to the September 7 export.
>
> **3. Package exactly what the downloader accepts.** Retain the existing naming contract with a new immutable tag `private-export-YYYYMMDD-HHMM` (the legacy word `private` is only an identifier, not an access restriction) and exactly one `htw-private-export-CORE-YYYYMMDD-HHMM.tar.gz` plus one `htw-private-export-FULL-YYYYMMDD-HHMM.tar.gz`. CORE must contain only these eight files: `race_records.parquet`, `race_conditions.parquet`, `course_profiles.parquet`, `course_segments.parquet`, `sources.parquet`, `races_summary.json`, `MANIFEST.json`, `README.md`. FULL must contain the same eight plus `features.parquet`. Shared files must be byte-identical. Use regular files with safe paths and unique basenames; each archive must remain within the current 8 GiB expanded-size limit. Put `ID-CONTRACT.md`, `COUNT-DIFF.md`, `FEATURE-FIELD-NOTES.md`, `SHA256SUMS.txt`, exclusion reports and every other audit sidecar in **separate release assets**, outside both tarballs.
>
> **4. Make the files easy to open and document all joins.** Also attach standalone copies of the Parquet tables and a consistent `.sqlite.gz` backup when feasible, with checksums and a short opening/querying example. Parquet can be queried with DuckDB/PyArrow and SQLite with ordinary database tools; CSV may be an optional convenience export, not a lossy replacement. In the manifest/data dictionary document table grain, columns, types, nullability, units, source, row counts and keys. Raw split strings are elapsed times; feature section/cumulative/finish times are minutes and paces minutes/km. The finish distance is 42.195 km and the last section is 2.195 km. Distinguish result IDs from uncertain cross-race runner IDs. Weather joins by a verified race edition; course overlays join by course and verified applicability. Their own table IDs are not runner-result IDs. Document transformations such as raw sex `X` becoming feature null.
>
> **5. Diagnose and correct source issues with evidence.** Prioritize Paris 2014–2018, where the September 10 source audit flags 204,796 non-increasing results. Compare original source values with imported columns to identify cumulative-versus-segment timing, column shifts, unit or pagination errors. Investigate missing 20 km measurements by edition, especially London, Honolulu, Athens, Valencia and Mexico City. Preserve source payloads, original values and correction provenance. Correct only source-supported errors. Do not interpolate splits or relabel a halfway measurement as 20 km. Keep genuine missing values and incomplete records.
>
> **6. Report completeness and missing measurements.** For each edition/source provide official finisher totals where available, ingested unique results, complete splits, eligible results, exact-age coverage, published age-band coverage, gender coverage, pending/error counts and source URLs. Mark full-field, partial, elite-only or unknown; a completed scrape is not proof of full coverage. Recheck sparse Tokyo/Melbourne data and Hamburg gender coverage. Provide sourced race dates/start times/timezones and actual halfway, chip/gun offsets, waves/corrals and finish/DNF/DNS status where available; leave unavailable measurements null. Provide historical course-validity evidence, not an assumed modern route for every year.
>
> **7. Prevent information leakage and reconcile exclusions.** Keep current/future race outcomes out of pre-race predictor fields. Label PB/ability, career-best, total-history counts and future-race features accurately. Supply separately named strictly prior-only benchmarks with documented cutoffs, or retain the consumer's existing recomputation from strictly earlier years. Document cross-race matching rules/version and ambiguity flags. Reconcile raw, deduplicated, missing/unparseable, non-increasing, quality-bound and eligible counts with disjoint categories; report overlapping diagnostic flags separately. Keep the feature `valid_splits` cohort distinct from the website pipeline's eligible cohort, explaining sex/force-drop and other differences.

> **8. Verify before announcing availability.** Check schema compatibility with `analysis/download_release.py`, `inspect_export.py`, `audit_expanded.py` and `build_extended.py`; verify ID uniqueness/set equality, row identity through available fields/timings, units, table counts, shared-file equality and archive checksums. Immediately test the published release and each asset without credentials; draft assets themselves are not publicly downloadable. Provide a validation report and the exact release tag, asset inventory, checksums and successful inspection/calculation run URLs. >
> **9. Provide operational access and a reproducible handoff.** Make the complete release and the ingestion/feature source code publicly readable. Publish the producer repositories or attach source snapshots with their commit IDs and reproducible commands; no repository invitation should be needed to reproduce an analysis. Supply the authoritative host/database paths, scheduler and job commands, write ownership, retries/pagination/watermarks, deduplication/correction policy, backup retention and last restore-test evidence. If direct live-host access is unavailable, explicitly say so; complete immutable releases are sufficient for full-dataset analysis, but not for operating the live ingestion service.
>
> Return a concise completion report with exact links and machine-readable audit results. Clearly list unresolved data gaps and their owners; do not mark unverified work complete.
