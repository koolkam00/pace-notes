## Configuration and launch

1. Create a free PostHog project for splithappens.run. Do not add a card or enable paid products for this setup.
2. In PostHog Project Settings > Session replay, turn on **Record user sessions**, keep console logs, network capture and canvas recording off, add `https://splithappens.run` and `https://www.splithappens.run` as recording domains, and add the URL blocklist regexes `^https?://[^/]+/(runners|your-race)(/|\?|#|$)` and `[?&]via=runner(&|#|$)`. In Project Settings > IP data capture, keep **Discard client IP data** on, and keep `/privacy` in step with it if that ever changes. Keep autocapture, dead clicks, exception capture, surveys, heatmaps and other products off; the client configuration below overrides the project for each of them anyway. (Cookieless server hash mode only matters for cookieless events, which the site no longer sends.)
3. Set these build environment variables on the Vercel project's Production environment:
   - `NEXT_PUBLIC_POSTHOG_KEY`: the project's public ingestion token, never a personal/admin API key.
   - `NEXT_PUBLIC_POSTHOG_HOST`: `https://us.i.posthog.com` for the US region, or `https://eu.i.posthog.com` for EU.
4. Redeploy after setting the variables; Next.js embeds them at build time. Neither value is obtained from the runner data. Keep tokens out of repository files.
5. Confirm the exact deployed commit and check PostHog's live events and a recording after visiting the canonical domain, submitting a search and opening a comparison (see [Verification](#verification)). Inspect event properties: no search query, names, selected record IDs or filter values may appear. Verify `/privacy` opt-out suppresses new events and recordings. Existing captured events may already be in flight when a preference changes.

The project can remain on PostHog's free plan without a card. Collection is limited by the plan's allowance; inspect current PostHog billing usage rather than assuming unlimited capture. Ad blockers, browser privacy preferences and explicit opt-out reduce measured traffic.

The anonymous ID lives in one browser tab's `sessionStorage`, so a "unique visitor" is a tab: one person with two tabs, or returning the next day, counts twice. Do not present visitor counts as individuals, and do not use them for return-visitor or retention analysis. PostHog derives location and bot signals from the connection IP during ingestion and then discards the IP (project setting above). Cookieless mode, used until October 2026, stripped the IP before that step, so September–October 2026 events have no location. A tab the browser restores keeps its ID, and so does a tab left open overnight.

## Events and starter dashboard

| Event | Meaning | Allowed custom properties |
| --- | --- | --- |
| `$pageview` | Initial load or navigation to another page; query-only filter changes do not add views | After a client-side navigation, the previous page view's `$prev_pageview_duration` (whole seconds, 0–3600), `$prev_pageview_max_scroll_percentage` and `$prev_pageview_max_content_percentage` (0–1 in 5% steps) and `$prev_pageview_pathname` (a clean path); the random `$pageview_id`/`$prev_pageview_id`. The first page view of a tab only: `utm_source` instagram, `utm_medium` social, `utm_content` bio/story/highlight/reel/post |
| `$pageleave` | The tab closes or leaves the site (SDK, on `pagehide`) | The same reading figures for the page being left, with its clean path as `$prev_pageview_pathname` (also its `$pathname`), and `$pageview_id`/`$prev_pageview_id` |
| `$web_vitals` | Page-speed measurements of a full page load, sent once by beacon when the page is first hidden (the site's, not the SDK's; no page-view ID, so join by `$pathname` and `$session_id`) | `$web_vitals_LCP_value`, `$web_vitals_FCP_value`, `$web_vitals_INP_value` (whole ms, 0–60,000) and `$web_vitals_CLS_value` (0–10, steps of 0.001) |
| `runner_search_submitted` | A non-empty search starts, including opening/restoring a shared search link | None |
| `runner_search_completed` | The latest non-aborted search returns or fails | `outcome`: matches, no_matches, error; `results`: 0, 1, 2-5, 6+ (matches found; not sent on error) |
| `runner_profile_opened` | A result group's race records finish loading | None |
| `race_comparison_opened` | Visitor presses View selected races | `selection`: one/multiple; `availability`: eligible/mixed/limited |
| `analysis_filters_applied` | Main, fast-start or weather filters are explicitly applied | Analysis ID and all/single course scope |
| `data_download_clicked` | Click on a project Release link or site data file; does not prove download completed | `destination`: release/site_data |
| `units_changed` | Visitor switches between miles and kilometres (pressing the units already shown sends nothing) | `units`: mi/km |
| `tool_used` | In a tool: the first change per page view (typing, choosing or pressing a button inside `.tool-workspace` or a region marked `data-tool-controls`), printing a page that has a tool, or a copied tool link. 13 `/tools/…` pages have nothing to edit (the five `/tools/marathon-pace/<goal>` and six `/tools/qualifying/<race>` pages, and the two pace charts, which can only print), so a tool-engagement rate over every `/tools/` page reads low for reasons unrelated to the tools | `action`: edit, print, copy_link |

Session replay sends `$snapshot` events (the recording itself) to PostHog's `/s/` endpoint; they are not analytics events and carry no custom properties (see below).

Every event of a tab that was given a variant of a running experiment also carries `$feature/<key>` with that variant's name (see [Experiments](#experiments)).

How the new signals are produced (added October 14, 2026; not yet deployed):
- **Reading depth.** Time on page comes from posthog-js (`lib/src/page-view.js`); the page a figure belongs to and how far down it was scrolled come from the site (`lib/analytics.ts`, `startReading` and `withReading`). The SDK keeps the tallest page it has seen since the last page view, and a client-side navigation lays out and scrolls the next page before that page view is sent, so a story read to the end and followed by a longer page counted as about half read (0.5 for `/stories/final-kick` → `/` on a phone); and a page view sent before the SDK had loaded named the page after it as its previous page. The site measures each page view's deepest scroll (the SDK's own formula: `scrollY / (scrollHeight − clientHeight)` and `(scrollY + clientHeight) / scrollHeight`, both with the tallest height seen) only while the address is still that page's, and `before_send` puts that page's path and depth on the next `$pageview` (as they were when that page view started) and on `$pageleave`, in place of the SDK's. They arrive on the next `$pageview` after a client-side navigation and on `$pageleave` (`capture_pageleave: true`) when the tab closes or leaves the site; both carry `$prev_pageview_pathname`, which autopilot/metrics.md reads on both. `before_send` keeps only the figures above, rounded on an integer scale (`Math.round(value * scale) / scale`: 1 for seconds, 20 for 5% steps, so 0.15 is stored as 0.15, not 0.15000000000000002), and drops values outside the range. A page restored from the back/forward cache (`pageshow` with `persisted`, `trackRestoredPage`) starts a new page view: posthog-js sent `$pageleave` for the old one as it went into the cache, so the new `$pageview` carries no `$prev_pageview_*` and that page view is not counted twice. An event the site asks for before the SDK has loaded is timestamped at that moment (`capture(…, { timestamp })` in `lib/analytics.ts`), so the first page's time on page is not cut short; the `$event_time_override_*` markers that adds are dropped. posthog-js sends any capture given options at once, one request each, so once the SDK has loaded the site's events are captured without options and join its 3 s batch (their capture time differs from the moment asked for by a microtask). Before October 15, 2026 every event carried the option, so reading the home page on a phone sent each section view as its own request (11 where the batch sends about 4).
- **Web Vitals.** Measured by the site with Google's `web-vitals` library (6.2.2, the version posthog-js bundles; a direct dependency, loaded with the lazily loaded replay policy, so not in any page's initial JavaScript) and sent by `measureWebVitals` in `lib/replay-policy.ts`; the SDK's own capture is off (`capture_performance: { web_vitals: false, network_timing: false }`). The SDK held the values the library reports as the page is hidden (LCP when the visitor never tapped, INP and CLS) for its flush delay and has no unload flush, so a visit that ended by closing the tab sent at most FCP. Now every value waits until the page is first hidden (closing the tab, leaving the site, switching apps), then all go at once in one `$web_vitals` by `sendBeacon` (`capture(…, { send_instantly: true, transport: 'sendBeacon' })`), which outlives the page. Each value is sent once per page load, or per restore from the back/forward cache; a tab hidden and shown again sends nothing more, so a CLS or INP that grows after the first time the page was hidden is not sent (the figures describe the visit up to then). Only full page loads are measured, not client-side navigations, and the values belong to the page that loaded (`$current_url` is the library's navigation URL, cleaned to its path), even when sent from a later page. INP exists only when the visitor interacted. `$web_vitals` carries no `$pageview_id`: the SDK's is the page view open when it is sent, which after a client-side navigation is the next page's; join Web Vitals by `$pathname` and `$session_id`. The project's remote config says `capturePerformance: false`; the client setting decides either way.
- **Tool use.** A delegated listener in `components/SiteAnalytics.tsx` sends `edit` for the first `input` or `change` event, or click on a button, in a tool's controls on each page view: `.tool-workspace`, plus any controls a tool keeps outside it, marked `data-tool-controls` (`TOOL_CONTROLS`): the pace calculator's view switch (`.tool-tabs`) and pace chart (`.pace-chart`), and the course chooser's list (`.course-chooser-list`: its sort, order, month and opening filters and column sorts). A tool that adds controls outside its workspace marks them the same way. It never reads a value or which element it was. Buttons that only jump down the page, print or copy the link are not edits (`NOT_EDITS`): ShareBar (`components/tools/ui.tsx`, class `.share-bar`) and buttons marked `data-not-edit` (every print button, and the projector's "Full result ↓" and "See the options ↓"); `verify-analytics` checks that every tool button calling `window.print()`, `onPrint(`, `scrollIntoView` or the projector's jump carries the marker. ShareBar's copy-link button sends `copy_link` once the clipboard write succeeds, and `print` comes from the window's `beforeprint` on any page with `.tool-workspace` or `.tool-share`. Other `.tool-share` rows hold edits (the pace chart's faster and slower paces, the projector's fallback buttons).
- **Feedback.** `components/PageFeedback.tsx`: Yes or No, then after No four fixed reasons, then "Thank you". No text box. The answer lives only in the component's state, once per page view; it sits before the story pagination (`StoryNav`), before the other tools (`ToolNext`, so on every tool and pace-chart page) and before the related tool on each analysis page.
- **Errors.** `site_error` is sent by the window's `error` listener (capture phase: a failed script or stylesheet under `/_next/` is `chunk_load`, other failed resources such as images are ignored, other errors are `js_error` or `chunk_load` when the message names a failed chunk), by `unhandledrejection` (`unhandled_rejection`), by `app/error.tsx` and `app/global-error.tsx` (`render`, or `chunk_load` for a failed chunk, using `chunkLoadFailed` in `lib/chunk-reload.ts`) and by `lib/data-fetch.ts` (`data_fetch`). `trackFailure` sends at most one per category per page view and five per page load, and every call names a literal category; the message is read only to tell a failed chunk apart and is never sent. A failed file usually reloads the page before any of the site's code has run (the `<head>` script in `lib/chunk-reload.ts`, which handles a script the page's HTML names), so the page it reloads into reports it: `SiteAnalytics` sends `chunk_load` once when the page was loaded by a reload (`performance.getEntriesByType('navigation')`) and `pace-notes-chunk-reload` holds a time less than 30 s old (`reloadedAfterChunkError`). The error pages and the analysis chart report a failure only when they do not reload for it, so each reload is counted once, by the reloaded page; the chart's chunk failing without a reload reports `chunk_load`. Before October 15, 2026 a failed file on a direct load was never reported. A file that fails again after the reload leaves the page without any of the site's code running, so nothing is sent (measured: no event within 12 s for the `/about` page chunk or the `main-app` script failing on every load) until an error page shows. A page that crashes before React starts, without a reload, sends nothing.
- **Data requests.** Every request the browser makes for the site's data goes through `dataFetch` (`lib/data-fetch.ts`): the stories and tools' insight files, runner search and race comparisons, the starting-pace and all-finisher evidence, the guide's comparison tables, the research-archive packs and `live.json`. It returns and throws exactly what `fetch` does, and reports a network failure or an error status as `data_fetch`, but not a request the page cancelled (`AbortError`). `verify-analytics` fails on any other `fetch(` in `app/`, `components/`, `lib/`, `hooks/` or `context/` (none runs only at build time today, so none is exempt).
- **Campaign tags.** The owner's Instagram links carry fixed tags (`?utm_source=instagram&utm_medium=social&utm_content=bio`, or `story`, `highlight`, `reel`, `post`). Each names a place many people see the same link: there is no value for a link sent in a direct message, which would tie the one person who opened it to everything that tab does, so such a link should carry no tags. `trackPage` reads them once, from the address the tab opened with, and sends them on that first `$pageview` only if every `utm_*` in the address is one of those values (one value each); otherwise none is sent. In a later task it removes every `utm_*` from the address with `history.replaceState`, whether or not analytics is on, keeping the rest of the query as written, so a copied tool link never carries them. `utm_*`, `fbclid` and `igshid` do not count as a runner's query for the handoff rule below.
- **Sections.** `components/SectionTracker.tsx`, mounted once in the root layout, watches elements marked `data-track-section="<id>"` (ids from `TRACKED_SECTIONS` in `lib/analytics-policy.ts`) with an IntersectionObserver and looks again after each client-side navigation. The home page marks its hero, each numbered chapter in order (`chapter-1` …), all stories (`stories`), the tools (`tools`), the ten analyses (`analyses`) and the closing call to find a runner (`cta`).
- **Paths.** Story and course pages keep their own path (`/stories/<slug>`, `/courses/<slug>`) from the literal lists `STORY_SLUGS` and `COURSE_SLUGS`; `verify-analytics` checks them against `lib/stories.ts` and `getCourseNames()`. Any other path under either section is recorded as the section, and the research archive stays grouped as `/packs`.

Use Web Analytics for visitors, page views, referrers and devices. A starter product dashboard should include daily unique `$pageview` visitors; top pages by `$pathname`; searches by `outcome`; race comparisons; download clicks; and a same-day funnel from `runner_search_submitted` to `runner_profile_opened` to `race_comparison_opened`. A per-tab identity cannot support return-visitor/retention analysis across tabs or days. Archive detail URLs are grouped at their section path (`/packs`); before October 14, 2026 course and story pages were grouped as `/courses` and `/stories` too; main analysis pages, the runner tools (`/tools/<slug>` from `lib/tools/registry.ts`) and the search pages retain their public path. Since October 14, 2026 (not yet deployed) story and course pages keep theirs too (see the list above). The search pages are the two pace charts and `/finish-times` (named in `lib/analytics-policy.ts`), the goal pages (`goalPagePath` for each `GOAL_PAGE_MINUTES` in `lib/tools/pace-chart.ts`: `/tools/marathon-pace/3-00` and so on) and the qualifying race pages (`/tools/qualifying/<key>` for each `STANDARDS` entry in `lib/tools/qualifying.ts`). An unknown goal or race (`/tools/marathon-pace/3-15`) is `/other`. `npm run verify:analytics` checks each search page, with its query string and fragment removed, and that every page in the sitemap keeps its own path or its section's, so a new page cannot fall to `/other` unnoticed. Tool inputs live in the query string and are always removed, so goals, splits and birth dates never reach analytics; in recordings the tools' inputs are masked and their results are left out (below).

## Data collection boundary

`lib/analytics-policy.ts` is the shared final allowlist for events, applied by the SDK's `before_send` hook; it also names the pages that are never recorded. `lib/replay-policy.ts` holds everything else for recordings (the `$snapshot` sanitizer, masking and blocking rules, the `session_recording` options) and the SDK options; it loads with the SDK, so it is not in any page's initial JavaScript, and its `sanitizeEvent` is the `before_send` hook (recording chunks to the snapshot sanitizer, every other event to the allowlist). Their tests are in `scripts/verify-analytics.cjs`.

**Identity.** `persistence: 'sessionStorage'`, `person_profiles: 'never'`. The SDK's random `distinct_id`, session ID (`$sesid`) and window ID live in `sessionStorage` (`ph_<token>_posthog`, `ph_<token>_window_id`, `ph_<token>_primary_window_exists`, `ph_<token>_session_registered_properties`), so they belong to one tab and are deleted when it closes. PostHog sets no cookie and stores nothing in `localStorage`. If sessionStorage does not work (blocked storage, a full quota), posthog-js would quietly fall back to `localStorage+cookie` persistence (`posthog-persistence.js`, `_buildStorage`), a one-year cookie and a `localStorage` entry with the device and distinct IDs; the site checks sessionStorage first (`sessionStorageWorks`) and uses `persistence: 'memory'` instead, so the ID then lives only in the open page. Its only `localStorage` calls are feature-detection probes that write and remove a test key in the same call (`__mplssupport__`, and `test` from the toolbar check) and a `removeItem('ph_debug')`; no 1.433.10 option skips them. Cookieless mode is gone: posthog-js refuses session recording with `cookieless_mode: 'always'`. `before_send` keeps the SDK's `distinct_id`, `$session_id` and `$window_id` only when each is a UUID, and drops the event otherwise.

**Analytics events.** Only the declared events and properties in the table above survive, with clean paths (no query string, fragment, unknown path or full referrer) and no `$set`/`$set_once`, person, session-entry or other campaign properties. Each keeps `$session_id` and `$window_id`, which link it to its recording. `$raw_user_agent` and the canonical `$host` stay for browser and device parsing.

**Recordings.**
- The recorder is bundled: `lib/analytics.ts` imports `posthog-js/dist/posthog-recorder` and `lib/replay-policy.ts` inside the same dynamic import as the SDK, because `disable_external_dependency_loading: true` stops the SDK fetching `lazy-recorder.js`/`posthog-recorder.js` from PostHog's CDN. None of the three enters a page's initial JavaScript. Measured on October 13, 2026 (dummy-key build): the recorder chunk is 208.9 KB (65.3 KB gzipped) and the replay policy chunk 7.0 KB (3.0 KB gzipped), loaded after hydration with the 312 KB (98.3 KB gzipped) SDK chunk, and only on production hosts with analytics allowed. What stays in every page (deciding whether to record, the blocked pages and the handoff marker) adds 0.3 KB gzipped (about 1 KB raw) to its initial JavaScript compared with `origin/main`; Next.js first-load JS is unchanged for `/` (138 kB) and `/tools/pace-calculator` (112 kB) and up to 1 kB higher elsewhere (`/runners` 225 to 226 kB).
- When recording starts: the SDK starts with `disable_session_recording: true`. `whenIdle` waits for the load event, three seconds and then an idle callback (5 s timeout), and only then lets `trackPage`/`syncRecording` call `startSessionRecording()`. rrweb's first full snapshot is one long task; leaving the story charts and race replay out of it (below) and `inlineStylesheetBudgetRules: 100` (later stylesheet rules are inlined in idle callbacks) shortened it on the homepage from about 610 ms to about 210 ms at 4x CPU throttling. Measured on October 13, 2026 (390 px, 4x CPU, analytics active, median of five loads, total blocking time over 14 s; control = the same build with the remote config blocked so the recorder never starts): homepage 670 ms against 599 ms (the review had measured 1,113 against 566 for `origin/main`), `/tools/pace-calculator` 213 ms against 134 ms (its first snapshot is now about 125 ms; about 90 ms of that is rrweb starting at all), `/stories/pacing-types` 468 against 356 ms (three loads). CLS stayed 0. The long task now starts at an idle moment at least three seconds after load (about 4–5 s after navigation in these runs), not during loading.
- Replay needs the project's remote config (`/array/<token>/config` on `us-assets.i.posthog.com`, a JSON request, not a script): it switches recording on and carries the URL blocklist. So `advanced_disable_flags` is no longer set; `advanced_disable_feature_flags` and `advanced_disable_feature_flags_on_first_load` keep the `/flags` request off. The client settings win over the project's for everything else: autocapture, rage and dead clicks, heatmaps, exceptions, web vitals and network timing (`capture_performance: false`), surveys, product tours, conversations, web experiments and the toolbar stay off.
- Masking: `maskAllInputs: true` with `maskInputFn` masks every input, select and textarea value as `***`, whatever its length (rrweb leaves hidden and file inputs unmasked; the site has neither). `REPLAY_MASKED_TEXT` masks the text (`maskTextFn`, also `***` whatever the length) and the descriptive and state attributes (`aria-label`, `aria-pressed`, `aria-checked`, `aria-selected`, `aria-current`, `aria-value*`, `title`, `alt`, `placeholder`, `value`, `data-*`; inline `style` is removed) of the regions that repeat what a visitor typed or chose: `.tool-workspace` (every tool), `.analysis-layout` (the analysis pages), `.personalized-guide`, the stories' `.which-card` and `.finish-lookup` calculators, the home page's marathon-time box (`.hero-goal`, experiment `home-hero-v1`), and every `[role="status"]`, `[role="alert"]` and `[aria-live]` element wherever it is (the tools' screen-reader summaries sit outside their workspaces). rrweb records which checkbox, radio button or option is chosen unmasked, so `before_send` deletes `checked` and `selected` from every recorded element and sets `isChecked: false` on input events, and masks any input event value again.
- Left out (`REPLAY_BLOCKED_ELEMENTS`, rrweb's `blockSelector`; replays show an empty box of the same size): every tool's results panel (`.tool-results`) and the course chooser's list of every course (`.course-chooser-list`, which follows the goal outside the workspace; it carries `ph-no-capture`), the SVG and canvas charts inside the masked regions (their shapes and positions encode the visitor's or a runner's times), the story charts (`.viz svg`), the animated race replay (`.replay`) and the hidden span Recharts adds to the page to measure axis labels (`#recharts_measurement_span`, which can hold a pace from the visitor's goal). The gender and division choices in the split check, pace band and qualifying checker sit in `ph-no-capture` elements. What a replay still shows: the page layout and class names, which links and buttons exist, scrolling, mouse movement and where the visitor clicks.
- Page addresses: `maskCapturedNetworkRequestFn` (which posthog-js also applies to rrweb Meta events and its `$url_changed`/`$pageview` markers) and `before_send` reduce every page URL in a recording to `https://splithappens.run` plus the clean analytics path. Links to the site's own pages (`a`/`area` `href`, `form` `action`, `formaction`) become the clean page address too; rrweb resolves in-page links such as the skip link (`href="#main"`) to the full current address, query string included. Every other link or source (`href`, `src`, `action`, `poster` and the like) loses everything from its first `?` or `#`, commas included; `srcset` loses it from each candidate; a URL in another attribute or in text loses its query, including site paths such as `/tools/split-check?s=…`. So neither a shared tool link, a Gmail draft link nor the current address carries what was typed (`maskAttributeFn` and `before_send`).
- Blocked pages: `/runners` and `/your-race` (and anything under them; `REPLAY_BLOCKED_PAGES`) show real runners' names, record IDs and search text. The links from a runner's profile into the split check and the pacing-pattern analysis put that runner's times in the query, so `RunnerContext` adds the marker `via=runner` (`runnerHandoffHref`) and `recordingBlocked` treats any page whose address carries it as blocked too, also after a reload, Back or Forward. A filter change or an onward link can drop the marker but keep the runner's race and times in the query, so once a tab has opened a handoff page, every later page with a query (other than `units` alone) stays unrecorded until the visitor opens a page without one, such as the site's navigation links (`noteRunnerHandoff` and `continuesRunnerHandoff` in `lib/analytics-policy.ts`, used by `pageRecordable` in `lib/replay-policy.ts`). `trackPage` notes the handoff as each page opens, before the SDK or the recorder is ready, so a quick filter change cannot hide it. The recorder's own page address then carries the `?via=runner` marker too, so `before_send` drops anything recorded there. The tab remembers this with one sessionStorage flag, `pace-notes-runner-handoff` (`1`, no other data), so a reload does not resume recording. Two known limits, checked in the browser on October 13, 2026: an onward link opened in a new tab (which gets no copy of the flag), and Back to such a page after the handoff has ended, can be recorded. Their text is masked like any tool or analysis page and their addresses carry no query, so no runner name, time or record reaches PostHog. `SiteAnalytics` calls `trackPage` on every navigation, which stops the recorder (`stopSessionRecording`) before such a page's view is sent and starts it again (`startSessionRecording`) on the next allowed page; a visit that lands on one starts with recording off. The project's URL blocklist pauses the recorder on the same pages as a second layer (add the `via=runner` regex there). `before_send` drops everything recorded from a blocked page's Meta event or `$url_changed` marker (the recorder keeps only the `?via=runner` marker in a handoff page's address so it can tell), or PostHog's `recording paused` marker, until the next allowed page's Meta event, and also drops any chunk recorded before a Meta event names the page. The containers that render names or search text carry `ph-no-capture` (search form, results, profile, selection, selected analysis and `RunnerContext`), so rrweb records only an empty placeholder for them even if a recorder were running.
- Not recorded: console logs (`enable_recording_console_log: false`) and network requests (`recordHeaders`/`recordBody` false, `capture_performance: false`). The bundled recorder also registers rrweb's console and network plugins, and `lib/replay-policy.ts` removes them before `posthog.init` (`__PosthogExtensions__.rrwebPlugins = {}`), so a project setting cannot turn either on. `before_send` drops any rrweb plugin event, canvas frames, JSON-LD and `rr_dataURL` image data. Canvas recording and cross-origin iframes are off.
- `compress_events: false` keeps each rrweb event readable so `before_send` can check it (requests are still gzip-compressed). Any compressed event is dropped.
- A `$snapshot` leaves with only `token`, `distinct_id`, `$session_id`, `$window_id`, `$snapshot_data` (the sanitized rrweb events), `$snapshot_bytes` (recomputed), `$snapshot_host` (`splithappens.run`), `$lib` and `$lib_version`: the fields posthog-js 1.433.10 itself sends (`lazy-loaded-session-recorder.js`, `_captureSnapshot`) minus its debug fields. In this version `$snapshot` goes through `capture()` and therefore `before_send` (`posthog-core.js`, `_runBeforeSend`).

Do Not Track, Global Privacy Control and the `/privacy` opt-out are checked before loading the SDK and before every capture, and a change stops the recorder (`trackPage` runs on each `ANALYTICS_CHANGED` or `storage` event; `respect_dnt: true` also opts the SDK out). With DNT or GPC the SDK and the recorder never load. The site's only analytics preference storage is the local boolean `marathon-analytics-disabled`.

Everything else the site keeps in the browser:

| Key | Where | Holds |
| --- | --- | --- |
| `marathon-analytics-disabled` | localStorage | `true`/`false`, the `/privacy` choice |
| `marathon-study-units` | localStorage | `mi`/`km` |
| `ph_<token>_*` | sessionStorage | PostHog's random tab, session and window IDs and registered properties (such as `$feature/<key>`) |
| `pace-notes-runner-handoff` | sessionStorage | `1` after a page opened from a runner's profile (below) |
| `pace-notes-exp:<key>` | sessionStorage | this tab's variant of a running experiment, such as `control` (see [Experiments](#experiments)) |
| `pace-notes-chunk-reload` | sessionStorage | the time of an automatic reload after a script failed to load (see [website architecture](WEBSITE_ARCHITECTURE.md#older-browsers-and-error-pages)); not analytics, never sent |

Analytics and recording failures must never block the site. Account access is needed to see the dashboard and recordings; visitor analytics is separate from the public research downloads.

The site can show two to four versions of part of a page and compare them, without PostHog feature flags (they would need the `/flags` request, and the version would arrive after the page painted).
- **Registry** (`lib/experiments.ts`, data only, the file the autopilot edits). The autopilot guard (`scripts/autopilot-guard.cjs`, autopilot/metrics.md §4 "Experiment registry and occupancy") reads it without running it, so it is exactly one `export const EXPERIMENTS = [ …literal entries… ] as const;`: comments, either quote, nested literal data and trailing commas are fine; imports, type declarations or annotations, spreads, expressions and later changes are not. Each entry has a unique `key` (3–40 characters, lowercase words joined by single hyphens), a `status` (`running`, or `paused` so everyone sees the control and nothing is reported), `pages` (where exposure counts: analytics paths such as `/` or `/tools`, each a page analytics keeps under its own path, or `['*']` for every page), an optional `area` (the part of those pages it changes, a lower-case hyphenated slug such as `hero`; left out, or `*`, it is the whole page), and this framework's own fields: `variants` (2–4, the first `control`), optional integer `weights` summing to 100 (default equal), the `started` date and a one-sentence `hypothesis`. At most two run at once, and two running experiments may share a page only in different areas (the guard's occupancy rule, which also counts experiments registered in the ledger). The `ExperimentDefinition` type, the checks (`experimentProblems`) and `EXPERIMENT_DEFINITIONS` (the registry typed as `readonly ExperimentDefinition[]`, so an entry of the wrong shape, or a registry without `as const`, fails `tsc` and the build) live in the framework, `lib/experiment-runtime.ts`. The build fails on a bad registry (`ExperimentHead` throws) and so does `verify-analytics`, which also reads the file with the guard's rules (a literal parser, never running it) and checks the result equals the module's value. Run with PR #57's guard, this file passed as an empty registry and with one running and one paused entry, and a registry with three running entries failed with "3 experiments would be active; at most 2 may be proposed, shipped or running" (October 15, 2026).
- **Assignment** (`lib/experiment-runtime.ts`, `components/Experiment.tsx`, `components/ExperimentVariant.tsx`; the framework, which does not change with the registry). `ExperimentHead`, in the root layout's `<head>`, renders the CSS and, when an experiment is running, a small inline script. For each running experiment the script reads `pace-notes-exp:<key>` from this tab's sessionStorage; if it is missing or not one of the variants it makes a weighted random pick and stores it; then it sets `<html data-exp-<key>="<variant>">`. If sessionStorage cannot be read or written the tab sees the control and no attribute is set, so it is not reported. The script reads nothing else and sends nothing. It is a classic, parser-blocking script, so it always runs before the first paint: the parser stops at it until the stylesheets before it have loaded (they block the first paint anyway) and builds no part of the body before it has run. The first version was an async module script, which with the CPU slowed 6x on a phone named the variant after the first paint in 7 of 10 cold loads (`/` and `/stories`), so the control showed first; the classic script was in time in all 30 loads measured (6x CPU; also with the stylesheets 400 ms late, and with every script and stylesheet 150 ms late). Next.js puts its stylesheet links and its own async script tags at the top of `<head>`, ahead of anything a layout renders, so the script cannot go before the stylesheets. The cost, measured: while it waits for the stylesheets Chromium holds back the page's script downloads (they start at once but finish only after the stylesheets: 626 against 202 ms with the stylesheets 400 ms late, 512 against 321 ms with every file 150 ms late), so React starts later when the stylesheets are slow (on `/`, 1.9 s against 0.4 s with the stylesheets 400 ms late, 1.8 s against 1.5 s with every file 150 ms late; on `/stories` 1.0 against 0.3 s and 0.79 against 0.72 s), while the first paint comes at the same time or earlier (on `/`, 0.88 against 1.46 s and 0.83 against 1.32 s, because the page's scripts no longer run before it). With no experiment running there is no script and no cost. The browser checks (S6) repeat the paint-order check on every run.
- **Markup.** `<Variant experiment="<key>" show="<variant>">…</Variant>` wraps each version (`data-exp-show="<key>:<variant>"`). The CSS hides every wrapped version except the one `<html>` names, with `display: contents` so the wrapper adds no box; with no attribute (no JavaScript, storage blocked, a paused experiment, or markup left behind after an experiment is removed) only `control` shows. `useVariant(key)` gives client code the variant: `control` until mounted, then the tab's.
- **Analytics.** After `posthog.init`, `lib/analytics.ts` registers `$feature/<key>: <variant>` for each variant named on `<html>` (`activeVariants`), so every event of the tab carries it. `before_send` keeps `$feature/<key>` only for a running experiment and one of its own variants. The tab's ID is per tab, so a variant is per tab too: a visitor with two tabs can see both versions.
- **Judging a result.** Compare page views (not visitors) on the experiment's `pages` by `$feature/<key>`: section views, tool use, reading depth, feedback, and `site_error` and Web Vitals as guardrails.

After the opt-out, nothing captured from that moment on is sent, and no request leaves after the SDK's next batch (3.5 s): events and recording chunks captured before the click can still go out in that batch, because posthog-js cannot drop its send queue.
- **I8** no page error other than those a scenario causes on purpose, no "Application error" screen, no error page where none is expected, in the old-Safari runs no lookbehind built or served, and no request the harness itself could not answer (a scenario's change to a page that throws fails that job, and the other jobs and the summary still run; so does an unhandled rejection).

S2 also compares its two runs (**I9**): the text and attributes a recording holds outside the masked and left-out regions must be the same for A and B, apart from the reviewed entries in `scripts/e2e/known-differences.json`, each with its reason (chunk script names, the box size and position rrweb keeps for a left-out panel, React's generated ids, whether a typed value was accepted, which comparison panel shows). Its values must not appear in its own traffic unless the other run, which never used them, shows them too (they are then page content). S8 fails a page whose initial JavaScript exceeds its budget by more than 1.5 KB (**I10**); after a deliberate change, `node scripts/verify-replay-e2e.cjs --only=S8 --write-budget` measures a new budget to commit with the reason.

The rules come from the site's own sources: the harness loads `lib/analytics-policy.ts`, `lib/experiments.ts` and the tools registry with the same TypeScript require hook as `verify-analytics`. Three are also written out in the harness (since October 15, 2026), so a rule widened in the site is still caught: the properties each event may carry (I2), the pages that are never recorded (I5) and PostHog's storage keys (I6). With the registry empty, the runs in S1 and S6 plant a variant of an unknown experiment on `<html>` and in sessionStorage and check that no event carries `$feature/*`. Once an experiment runs, they plant its last variant and check that every event carries exactly that.
